The later [minimal two-resident launch](MINIMAL_STEWARD_RESEARCHER_LAUNCH.md) is the
preferred next-cycle option. Its section 7 selects the applicable items here and
defers Intake admission, broad unattended recovery and autonomous installation.
Use its two-resident roster and direct operator mail. Steward is resourcing-only;
Researcher receives its research campaign from Rawley, with no Steward approval.
The concrete current build path is [launch readiness](minimal-research-launch/LAUNCH_READINESS.md).

Prepared 2026-10-14. Companion to the [Researcher proposal](researcher-resident-proposal.md),
[node](researcher-resident.node.json) and [assembly fragment](researcher-resident.launch-fragment.json).
**No item below is marked complete by writing these documents.** “Existing” means
the selected source contains the mechanism, not that this deployment exercised it.

The first release can admit Researcher to prepare its portfolio. Live experimental
use and unattended recursive improvement require progressively stronger gates.
The entries distinguish configuration work, live qualification and possible source
additions so this does not become an unnecessary host redesign.

## Suggested first acceptance scenario

Use a modest topology or instruction improvement whose benefit can be inspected
without changing the supervision machinery itself. This isolates the research
workflow while exercising real dispatch and useful work.

1. A delegate proposes two opportunities with source evidence; Researcher rejects
   or defers one for a stated reason, applying Rawley’s initial campaign and direct coaching.
2. Researcher acts on its launch steering without a Steward conversation and opens one
   real `runtime-improvement` project coordinate. The delegate builds the baseline/candidate contract
   within that work and returns exact files and checks.
3. Researcher starts an independently supervised experiment and persists its
   handle. Pause production through the owner; observe that Researcher and Intake
   are unavailable while the coordinator continues.
4. The trial includes useful project work and at least one intentional topology
   change within the qualified monitoring load. Reconcile added resident/project
   coverage through normal checkpoints; preserve all original assessments.
5. The coordinator authors a justified decision, settles its trial and restores
   the exact baseline. Researcher consumes the outcome, records its own acceptance
   judgment and releases the outer project attachment after real settlement.
6. Exercise one representative failure/cancel through the same lifecycle owner,
   showing unresolved cleanup cannot be mistaken for another free experiment slot.
7. Promote one accepted artifact through its real owner, observe production
   adoption and evaluate its use. Until this last step, call the result a qualified
   experiment, not a completed recursive-improvement cycle.

## Assertions for any required implementation

Use scoped Retrace assertions against **F6** for integrated host changes. Reuse
the existing native-supervision witnesses and their actual broker/process/store
carriers; do not replace native agent returns with host-side fabricated reports.
Add focused companions only for genuine process/kill/recovery boundaries that
cannot be safely combined in the main screenplay. The rows below are proposed
oracles, not claims that these new cases have already passed.

| Assertion | Canonical witness / required observation |
|---|---|
| Sponsor origin and attribution | Accepted execute-code binding, exact project REPL/submission, capacity attachment and immutable experiment origin refer to the same native initiating work. |
| Independent lifetime | Actual coordinator process and retained native session/REPL continue through initiating-runtime pause; fresh monitor terminals and original delivery prove real reviews. |
| Distinct nested capacities | Production ledger has one sponsor; trial ledger independently governs two test project attachments; exhausting trial capacity changes neither production occupancy nor entitlement. |
| Correct release boundary | Settled outcome + no outstanding ordinary work permits one outer release; pending cleanup or unresolved accepted external obligation does not masquerade as whole-experiment settlement. |
| Cancel/retire/recover | Exact request receives stop/failure disposition, original owner and dependent work settle, unrelated lease/hold survives, repeat reconciliation is idempotent. |
| Reentry and delivery | Saved handle recovers original outcome after missed notice/renewal; duplicate event causes no second launch or promotion; original result becomes model-visible. |
| Activation execution | Native queue returns before an independent foreground consumer drains/stops; exact expected release and main-line commit checked; consumer survives caller loss and records final disposition. |
| Activation scope | Same-instance retain accepted when otherwise valid; changed instance/assignments refused under current contract with no installation effect. |
| Promotion and drift | Exact tested head/base and configured resource binding used; changed head/base/package/launch is not accepted on stale evidence; merge, install and package adoption have distinct receipts. |
| Useful output | Test workload yields the declared artifact through real model-authored work; baseline/candidate evidence reaches the assessing model; success is not inferred from process completion. |

Physical deployment/restoration and actual-provider timing still require an
attended live run; provider-fake F6 cannot substitute for them. Human benefit and
Rawley's judgment are evaluated from actual use, not fabricated fixture approval.

## Defer unless a demonstrated need arises

- Parallel experiment scheduling and dynamically expanding the production project
  slot universe. Begin with one sponsor project and one active experiment.
- A new host opportunity registry, research duty kind or convergence scoring engine.
- Permanent resident monitor agents. Existing finite monitors and checkpoint
  assignments serve the initial need.
- Arbitrary recursive experiments targeting an allocator already leased by a trial.
- A generalized autonomous deployment service. Prove the exact existing queued
  activation request and independent consumer handoff first.
- Self-experimentation on the coordinator's own lifecycle implementation while it
  is supervising. Current request validation requires identical shared
  `live_testing`, `host` and `launch_config` owner bytes across coordinator/trial;
  changes there need a separately qualified common owner version and external
  supervision, not an assumed unrestricted A/B experiment.

proposal. Refresh installed state and all actual resources before using this list
