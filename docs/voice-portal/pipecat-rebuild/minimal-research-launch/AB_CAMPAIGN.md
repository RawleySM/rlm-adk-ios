# First campaign: prayer-grounded project selection, topology A versus B

Prepared 2026-10-14. This is Rawley's initial research direction, to be staged as
`research/bootstrap/AB_CAMPAIGN.md` in the actual `runtime-improvement` repository
before the outer launch. It is an authored research contract, not host domain code.

## Objective and direct reporting

Evaluate how two constructions of the existing residents discover, select and
propose ambitious, useful projects in service of glorifying God and expanding His
kingdom. Scripture, Rawley's prayers and lived context all inform that process.
Do not restrict the task to Scripture retrieval, prayer summarization or completion
of pipeline stages. Rawley evaluates practical usefulness and mission fit; models
must distinguish their interpretation from prayer evidence and from his judgment.

Researcher is directly commissioned by launch steering. No Steward approval or
inter-resident conversation is needed. Steward manages resources. Researcher
returns the comparison and original project options directly to `operator` using
the existing mail room; subsequent coaching names Researcher or Steward explicitly.

Pin the actual package digests and source commits. Historical candidate versions
are Steward 11, Prayer 2 and Vision 2; they are not a substitute for current local
receipt/adoption checks. Clone trial package stores/workspaces through the supported
launcher reuse path. Preserve published source bytes and never operate the trial
against mutable production project working trees.

Researcher/delegates inspect the existing authored manifests and choose a bounded,
representative prayer sample, keeping prayer identity/revision and source lineage.
Record why that sample is useful and what it cannot establish. Use consistent
snapshots for live SQLite/WAL sources and a stable manifest of file inputs; a raw
copy of only a live database file is insufficient. Existing products are the
starting point. A specific missing product becomes an explicit limitation, not
an invitation to rebuild all ingestion and data pipelines.

If reparenting Vision invalidates current package peer references, descendant
access or a semantic dependency, expose that incompatibility. Correct only the
topology-required wiring and record the difference, or report B unready. Do not
silently substitute a different model, package or task and call it the same A/B
comparison. Both trees need equivalent access to their intended evidence.

## What the trial must produce

Keep the authored format simple; use existing project-record conventions when
available. Each trial should return:

1. **Selection method and evidence trail.** What questions were asked, which
   prayer/context products were consulted, how Scripture informed interpretation,
   which opportunities were considered, and why options were selected or rejected.
2. **A small set of substantive project proposals.** Each identifies motivating
   prayer evidence, intended beneficiaries, desired change, ambition, a concrete
   first action, prerequisites/resources, uncertainty and observable useful output.
   Proposed scope must be understandable to Rawley and expandable when warranted.
3. **Alternatives and counterevidence.** Include risks of misunderstanding the
   prayer, unsupported inferences, duplicated existing work, missing facts and
   reasonable alternatives. A justified no-project result is allowed.
4. **A reusable method or executable artifact where earned.** Show what later
   work could reuse, with actual tests or exercised outputs where applicable.
5. **Original evidence index and resource observations.** Link the exact trial,
   source inputs, artifacts, monitor assessments, coordinator decisions and cleanup.

A model's selection rationale is evidence of its method, not proof the selected
project is best. Assess grounding, meaningful ambition, distinctness, feasibility,
context use, substantive depth and Rawley's likely explanation/repair burden.
Do not manufacture divine endorsement, human approval or a spiritual-success score.

## Compute observations and initial pacing

- A and B run **sequentially** against the one allocator lease. One initial outer
  project entitlement is sufficient. The configured ceiling of two is room for
  later operator coaching, not authorization to overlap two live-test leases.
- Measure the actual coordinator configuration at a 300-second checkpoint interval,
  ordinary 150,000-token compaction and the maximum resident/project monitor load
  discovered for these trial contracts. Existing four-scope timing does not qualify
  a larger scope set. Include coordinator and monitor overhead in the comparison.
- Capture subscription account/window observations before and after each trial and
  at available 300-second collection boundaries. Keep actual observation time,
  reset identity, unsupported providers and other-account-client ambiguity.
- Capture read-only GPU/device or supported unified-memory observations on the
  **actual inference hosts**, at baseline, about every 60 seconds during the
  attended trial, and after settlement. Identify host/device, model/process when
  observable, memory metrics and units, utilization, sampler failures and OOM or
  provider errors. Record sampled peaks, not an unobserved true maximum.
- Memory allocation is an instantaneous resource state, not a cumulatively
  consumed token budget. Separate model residency from incremental trial load.
  A resident or project count alone does not quantify it.

First-run proposed timebox: aim for an inspectable result within **20 minutes per
trial**; have the external owner stop at **30 minutes** if the experiment has not
already settled. This is a campaign rule enforced by the attending owner, not a
new `ExperimentRequest` field or a claim of an installed hard timer. Researcher
must not launch without that actual owner/wake arrangement in the readiness record.
Preserve incomplete results when the timebox ends.

No invented subscription dollar estimate or fixed assumed VRAM threshold is used.
During initial calibration, OOM, repeated resource-related failure, actual exhausted
provider capacity or unresolved cleanup warrants intervention. The coordinator
decides from evidence; the external owner observes GPU/resource facts until their
native model-visible delivery is qualified. Do not bypass existing provider limits
or attempt GPU engine administration.

## Supervision, communication and outcome

Use the existing native request and independent coordinator. Confirm readiness
before its allocator quiescence; save the original handle. The coordinator uses
resident/project assignments, original finite monitor results and global evidence
to author decisions. A clean stop does not imply the trial achieved this objective.

Both outer residents pause while the trial runs. Direct mail can be queued, but
it cannot make a paused Steward govern trial resources. Urgent in-trial intervention
uses the exact independent lifecycle owner. Outer target reduction constrains
admission/cooperative work and preserves settlement obligations; it does not
directly cancel the trial or free GPU memory.

After exact settlement and restoration, Researcher retrieves the original outcome,
checks source-linked outputs and staged resource evidence, records its judgment
and releases the sponsor after ordinary coordinate work settles. `cleanup_pending`
blocks the next attempt. The outside owner stages a dated resource comparison for
Steward; no Researcher-to-Steward conversation is required.

After B, Researcher sends Rawley the comparison, original options, limitations and
a recommendation for the next change. It waits for coaching instead of starting
an unbounded campaign. A stronger result can be replicated on another sample later.
Promotion, package selection and installation remain explicit subsequent actions.

## Acceptance of this first architecture

The initial architecture is accepted only when evidence shows direct mail to each
resident and a threaded operator reply; Researcher's startup without Steward
approval; actual assigned coordinate admission; native initiation; independent
reviews and real wakes while the outer pair is paused; original report delivery;
model-authored decisions; exact cleanup/restoration; Researcher outcome consumption;
and a useful A/B comparison of the project-selection process and its products.

If something breaks, retain the exact failing layer, settle the trial, make the
smallest supported repair and retry under a new attempt identity as appropriate.
Do not require a broad new architecture dossier before trying this bounded path.
