IOS-1 Native iPhone continuous audio feasibility

Executive Recommendation

Architecting a continuous, indefinitely running native audio capture session on an iPhone for a single-user SwiftUI portal presents severe engineering friction when reconciled against modern iOS execution policies. Based on exhaustive research of the AVFAudio and AVFoundation frameworks operating on an iOS 17 baseline through the iOS 26.5 iterations, the explicit goal of 24/7 background audio capture without sustained user interaction is natively hostile. While publisher documentation asserts that appending the audio value to the UIBackgroundModes array permits background recording, measured device evidence demonstrates that the iOS task scheduler aggressively enforces process limits, frequently terminating background audio applications with a SIGKILL command after approximately 50 seconds of locked-screen background execution.  

However, a conditional pathway to feasibility exists. A continuous background audio architecture can survive indefinitely if the application couples the AVAudioRecorder or AVAudioEngine implementation with an active ActivityKit Live Activity possessing the frequentPushesEnabled capability, bypassing reliance on standard Voice over IP (VoIP), WebRTC, or PushKit entanglements. Therefore, the executive recommendation is to proceed with the native Swift workspace (RawleySM/rlm-adk-ios) utilizing a highly specific, hybrid architecture. This architecture must heavily leverage AVAudioSessionCategoryPlayAndRecord for hardware abstraction, the AVAudioApplication singleton for modern permissions, and a non-dismissible Live Activity to anchor the application's background execution priority.  

The user-selected gold standard for voice provider transport—OpenAI's Realtime API utilizing the gpt-4o-mini-realtime-preview model—is economically and technically viable, provided the architectural design severely restricts continuous network streaming. Streaming 24/7 audio to an endpoint billing at $10.00 per one million input tokens is financially untenable for continuous quiet periods. Thus, the system must utilize explicit, app-controlled quiet states. Because local prayer capture requires the microphone to remain active to save long silences, the application cannot utilize the global AVAudioApplication.shared.setInputMuted(true) command. Instead, the local execution backend must silently write the continuous audio buffers to disk while purposefully severing the outbound WebSocket connection to OpenAI until an explicit user wake command is detected.  

The nearest alternative to a pure native execution is a hardware-tethered companion device, such as a wearable Bluetooth microphone equipped with local buffer memory. This companion device would continuously record and subsequently transmit batch data to the iPhone via Bluetooth Low Energy (BLE) background tasks, operating under the Acts as a Bluetooth LE accessory background mode. This alternative fundamentally changes the system architecture from a software-only portal to a hardware-reliant ecosystem and should only be pursued if future Apple OS updates aggressively deprecate the Live Activity background-bridging loophole.  

Architectural Feasibility of Continuous Native Capture

The engineering of continuous native iOS capture requires a complete mapping of the Core Audio Hardware Abstraction Layer (HAL) routing, the AVAudioSession configuration, and the modern iOS permission lifecycle. The foundational layer of this application relies on the AVFAudio framework, which dictates how the application negotiates priority with the operating system, competing background media applications, and physical hardware peripherals.

Baseline Capabilities and the iOS 17 Paradigm Shift

Beginning with the iOS 17 baseline, Apple introduced a paradigm shift in how microphone permissions and application-level muting are handled. Previously, developers utilized AVAudioSession.sharedInstance().requestRecordPermission to negotiate user consent. In iOS 17 and subsequent versions, this mechanism was deprecated and replaced by the AVAudioApplication singleton. The application must now interrogate AVAudioApplication.shared.recordPermission and utilize AVAudioApplication.requestRecordPermission(completionHandler:) to initialize capture safely. The deployment target must strictly enforce these newer interfaces to avoid legacy compatibility failures.  

This transition to AVAudioApplication introduces the setInputMuted(_:) function, which accepts a Boolean value to mute all sources of audio input exclusively within the application. Crucially, this setting is isolated to the specific app and does not affect the physical device's hardware mute state. While highly useful for absolute privacy, utilizing this API natively conflicts with the requirement for prayer capture. If the user engages quiet mode, but prayer capture must tolerate long silences and save to disk, setInputMuted(true) cannot be called, as it zeroes the input buffers at the OS level before they reach the app. Explicit quiet must therefore be engineered at the routing layer within the RLM-ADK execution backend, persisting the tap buffers to storage while muting the outbound network pipeline.  

To prepare the system for both local capture and proactive speech playback, the application must interact with AVAudioSession. The default audio session supports playback but strictly disallows recording, and it universally obeys the physical Ring/Silent switch on the iOS device. To bypass these restrictions and ensure proactive speech functions on request, the application must instantiate the .playAndRecord category. When .playAndRecord is active, the application can emit audio—such as calendar preparation alerts or project phase inquiries—even if the hardware Ring/Silent switch is engaged, fully satisfying the requirement that app-controlled quiet dictates playback, not the physical switch.  

The configuration of this session requires meticulous application of category options. To ensure seamless transitions between AirPods, vehicle Bluetooth systems, and the internal device microphones without crashing the capture engine, the AVAudioSession must be instantiated with the .allowBluetooth, .allowBluetoothA2DP, and .defaultToSpeaker options. The .defaultToSpeaker option is particularly vital for the portal; without it, audio playback during an active recording session defaults to the low-volume earpiece receiver designed for cellular calls, rendering proactive room-scale speech entirely inaudible.  

Background Execution Limits and the 50-Second OS Culling

The most significant existential threat to the continuous audio feasibility is the iOS background process scheduler. Apple's documentation asserts that enabling the audio value within the UIBackgroundModes array of the application's Info.plist permits an application to play audible content and capture audio continuously in the background. Under a theoretical reading of this documentation, initializing an AVAudioEngine or AVAudioRecorder instance while the application is in the foreground, and subsequently locking the screen, should allow infinite recording.  

Measured device evidence heavily contradicts this documentation on modern operating systems. On current iterations extending through iOS 26.5, the OS scheduler aggressively terminates audio-recording applications after approximately 50 seconds of locked-screen background execution with a SIGKILL command. This termination occurs without ever invoking the AVAudioSession.interruptionNotification, leaving the application unable to serialize data, save contextual state, or gracefully close active file handlers. The termination happens despite the system API backgroundTimeRemaining reporting maximum values upon the app entering the background.  

Engineering analysis of applications that survive this culling reveals that standard entitlements and background task APIs are insufficient. Applications relying strictly on UIBackgroundModes: audio, fetch, or processing inevitably succumb to the scheduler. The BGTaskScheduler and BGProcessingTaskRequest frameworks offer deferred background execution intended for system-optimized windows, but they do not provide the continuous runtime required for an always-listening portal. Furthermore, attempting to use background URLSession tasks for large audio file batching frequently results in complete stalls due to scheduler budget policies, severely impacting long-form uploads.  

To bypass this undocumented system behavior, the execution architecture must bridge the foreground-background boundary using ActivityKit Live Activities. Measured device extraction confirms that utilizing a standard AVAudioRecorder combined with a Live Activity that explicitly requests frequentPushesEnabled completely circumvents the 50-second SIGKILL limitation, allowing the capture session to persist indefinitely. The Live Activity serves as a persistent, non-dismissible anchor to the user's lock screen and Dynamic Island, signaling to the OS scheduler that the process remains intimately connected to a primary user interaction loop, thereby artificially elevating its task priority above the background culling threshold.

Hardware route changes represent a severe architectural hazard. When a user connects AirPods or enters a vehicle equipped with Bluetooth Hands-Free Profile (HFP), the Core Audio HAL dynamically rewires the device's physical audio layout. If the application utilizes AVAudioEngine and installs a tap on the inputNode using installTap(onBus:bufferSize:format:block:), a route change frequently corrupts the internal buffer.  

Measured evidence indicates that switching from Bluetooth peripherals back to the iPhone's internal systems causes the AVAudioEngine to silently halt audio routing. The tap block continues to execute, but the buffer.floatChannelData delivers entirely zeroed-out frames representing digital silence. This occurs without throwing any catchable Swift errors or OSStatus codes, effectively blinding the application. Furthermore, calling engine.reset() or disconnecting and reconnecting the inputNode fails to recover the hardware link. The only engineered solution that reliably recovers the audio graph is to cleanly deallocate the entire AVAudioEngine instance, release the inputNode, and completely re-instantiate the graph upon detecting an AVAudioSession.routeChangeNotification.  

An additional systemic bug observed during extended continuous capture involves the HAL returning a 2003329396 (the what four-character code) error when attempting to route the built-in microphone into the active session. This occurs even when the system registers that isInputAvailable is true and no competing clients are observable. To mitigate this, the architecture must implement a watchdog timer that monitors the root mean square (RMS) or peak power levels of the incoming audio buffers. If prolonged absolute digital silence is detected while the explicit quiet mode is disengaged, the watchdog must assume a HAL failure and force a full session teardown and restart.  

Voice-Provider Transport and Cost Economics

The user-selected performance gold standard for the voice transport layer is OpenAI's live voice architecture. To architect this correctly within a native SwiftUI portal, it is critical to distinguish between the consumer ChatGPT Pro offering and the developer-facing Realtime API.

The ChatGPT Pro subscription provides an encapsulated, rate-limited consumer application experience operating on a proprietary WebRTC transport. It utilizes a flat-fee billing model but cannot be headless-integrated or systematically controlled by a native SwiftUI application graph. Therefore, the native workspace must connect directly to the official OpenAI API utilizing the gpt-4o-mini-realtime-preview model. This model is explicitly designed to handle low-latency, multimodal interactions via WebRTC or WebSocket interfaces, allowing the user to naturally interrupt, correct, and transition between conversational activities dynamically.  

The financial modeling for a continuous audio portal running against the gpt-4o-mini-realtime-preview API establishes a primary structural constraint. The API billing is strictly usage-based and separated distinctly into text and audio tokens. Text tokens are highly commoditized, priced at $0.60 per one million input tokens and $2.40 per one million output tokens.  

Audio tokens, conversely, dictate an extreme premium. Audio input is billed at $10.00 per one million tokens, while audio output incurs a massive cost of $20.00 per one million tokens. OpenAI does support a caching mechanism for input, severely reducing the cost of redundant context; cached audio input drops to $0.30 per one million tokens.

If the application were to continuously stream raw captured audio from the iOS device to the OpenAI Realtime API for 24 hours a day, the token consumption would be economically ruinous. A standard 24kHz audio stream generates tens of thousands of tokens per minute, regardless of whether the user is speaking or maintaining a long silent prayer.

Thus, the system architecture must strictly separate the local recording phase from the conversational voice session. The native app will capture continuously to local storage. When the user explicitly breaks the quiet state—initiating a voice session for scripture playback, interview mode, or calendar preparation—only then does the application open the WebSocket/WebRTC connection to the gpt-4o-mini-realtime-preview endpoint. Once the conversational activity concludes, the session is aggressively torn down, isolating token costs strictly to active engagement periods while the background local recording continues unabated.  

Data Strategy and Domain Projections

The backend execution relies on heterogeneous independent source products: prayer transcripts, sermon text, temporal calendar data, and complex biblical historical contexts. Because there is no selected consolidated knowledge backend, the extraction frameworks must project into distinct schemas, and domain projections belong entirely to consuming projects.

For the biblical contextual layer, the application relies on the "Theographic" dataset. Theographic is a highly structured, CC BY-SA 4.0 licensed metadata schema containing over 4,800 people, places, and events, heavily cross-linked with 53,000 verse citations. This dataset provides a relational and graph-ready mapping of biblical history, distinct from generalized temporal extraction frameworks or dynamic LLM-generated nodes found in Neo4j or Microsoft GraphRAG. Theographic provides absolute, immutable historical truth as a foundational reference plane.  

The schema includes 19,391 scholarly lexicon entries (including the Brown-Driver-Briggs Hebrew Lexicon and Abbott-Smith NT Greek), 31,280 morphologically tagged verses, and 4,299 named entities. The Theographic dataset acts as the definitive ontology for the voice session's creative workflows. When the user initiates a long research request or a storyboard interview, the resulting durable action items map the transcribed user intent against the Theographic entities.  

For instance, if a user requests a contextual deep-dive into the lineage of David during a conversational session, the local backend utilizes capabilities like explore_genealogy and explore_person_events against the Theographic graph to construct an ancestor chain and chronological timeline. The OpenAI gpt-4o-mini-realtime-preview model is then fed this structured text data as system-prompt context. Because text input is heavily subsidized ($0.60 per 1M tokens) compared to audio ($10.00 per 1M tokens), the architecture maximizes cost efficiency by translating the massive Theographic graph context into text tokens, while reserving the audio tokens purely for the user's spoken interface and the model's synthesized voice output. Source identities, revisions, and evidence citations derived from Theographic remain completely intact within the RLM-ADK execution backend, preserving the scholarly integrity of the final produced reports, books, or separate websites.  

Concrete Design Implications for RLM-ADK

Translating these rigid constraints and capabilities into the RawleySM/rlm-adk-ios native SwiftUI workspace necessitates a highly decoupled architecture. The native application must preserve existing safeguards, explicitly avoiding any hypothetical security-hardening sandboxes or LLM-isolation wrappers, focusing purely on the mechanics of raw audio transport, system lifecycle management, and strict local storage optimization.

The Minimal Capture Architecture

The core of the application must be split into two isolated, concurrently executing modules: the Local Capture Pipeline and the Conversational Transport Pipeline.

The Local Capture Pipeline is instantiated immediately at application launch following permission grants. It utilizes an AVAudioEngine with an installTap on the inputNode. The AVAudioSession is permanently set to .playAndRecord with .defaultToSpeaker, .allowBluetooth, and .allowBluetoothA2DP. The tap accumulates PCM buffers at an optimized sample rate.  

A continuous native recorder accumulating data 24 hours a day necessitates highly optimized storage and power assumptions. Utilizing uncompressed LPCM (Linear Pulse Code Modulation) at 48kHz, 16-bit stereo consumes approximately 11.5 MB per minute, or roughly 16.5 GB per 24 hours. To preserve device storage, the installTap buffer must encode to an efficient format before persisting to disk. Encoding to AAC (Advanced Audio Coding) at a 64 kbps bitrate reduces the storage footprint to approximately 0.48 MB per minute, totaling under 700 MB per day. This is well within the acceptable storage parameters of a modern iPhone, allowing long-form prayer capture to persist safely.  

The Conversational Transport Pipeline remains dormant during explicit quiet or continuous prayer capture. Upon user wake, it establishes the bidirectional WebRTC or WebSocket stream to the OpenAI Realtime API. Inbound proactive speech triggers from the RLM-ADK execution backend (such as calendar prep) are queued locally during quiet states. Upon wake, the queue is released, the OpenAI connection is established, and proactive speech ensues. When outside of quiet mode, the app uses the active AVAudioSession to announce calendar preparation. Because the category is .playAndRecord, the audio successfully routes to the primary speaker regardless of the physical Ring/Silent switch status.  

Signing and Distribution Considerations

The application workspace utilizes a paid Apple Developer Program membership. However, it is a critical design judgment to recognize that a paid Developer Program certificate does not bypass OS-level resource limits or grant immunity from the iOS task scheduler. The 50-second SIGKILL for background audio applies equally to App Store, TestFlight, and ad-hoc distributed binaries.  

The only distribution variance is that obtaining the entitlements required for the Live Activity and background modes requires accurate provisioning profile configuration in Xcode. The application must explicitly declare NSMicrophoneUsageDescription in the Info.plist, providing a clear purpose string (e.g., "Continuous capture for contextual journal and prayer logging"), otherwise the application will instantly crash upon invoking AVAudioApplication.requestRecordPermission.

Important Unresolved Facts

Despite rigorous documentation and measured evidence, several critical system behaviors remain unresolved and require empirical observation during the physical proof plan:

Empty Input Route HAL Bug

Under certain conditions, currentRoute.inputs returns completely empty, and the HAL triggers a 2003329396 (what) error despite isInputAvailable returning true. It is unproven what specific system lock triggers this state, and whether resetting the session recovers it without an app restart.

Zero-Buffer Tap Degradation

The exact mechanism causing AVAudioEngine.inputNode to silently deliver all-zero PCM buffers after a Bluetooth route change, rather than throwing a format mismatch or stream error, is fundamentally undocumented.

Live Activity Longevity Threshold

While binding the audio session to a Live Activity reliably circumvents the 50-second background kill, the maximum theoretical duration of a Live Activity (traditionally capped at 8-12 hours by the OS) remains a limiting factor for true 24/7 perpetual capture.

Volume Normalization Interruption

When utilizing AVAudioSession alongside system overlays (like Siri), audio can occasionally resume at a reduced volume until the overlay is fully dismissed, despite proper .shouldResume handling. Mitigation for instant full-volume resumption remains an open system quirk.
