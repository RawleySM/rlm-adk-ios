For conversational phases, an eyes-free Human-Computer Interaction (HCI) approach is paramount. Human-Computer Interaction Foundations for Continuous Voice Environments

The design of a continuous, single-user native iOS portal relies heavily on established research in ubiquitous computing, interruptibility, and conversational turn-taking. A system that proactively manages calendar preparations and project phases while respecting explicit quiet demands a highly nuanced understanding of cognitive load and human attention.

Interruptibility and the Proactivity Dilemma

A core challenge in continuous voice interfaces is the proactivity dilemma, which involves balancing the utility of just-in-time information against the severe cognitive cost of interrupting the user's current physical or mental context. Historically, human-computer interaction research has framed user-interruption as a complex event requiring careful mediation. McFarlane's seminal taxonomy of human interruption establishes that unmediated, immediate system speech often forces a break in the user's execution-evaluation cycle, leading to high cognitive costs and task abandonment.

To mitigate these disruptions, modern Attentional Computing Systems utilize turn-taking paradigms and contextual awareness to determine interruptibility. However, relying purely on availability inference—guessing when the user is amenable to proactive speech based on calendar data, ambient noise, or device accelerometer states—is highly prone to failure. Inferred availability cannot reliably account for internal states of reflection, deep work, or prayer. Therefore, the IOS-2 design enforces a strict behavioral hierarchy wherein explicit control permanently supersedes all inferred availability. When the user invokes the explicit quiet state, the system's proactivity is entirely suppressed. Calendar timers, departure warnings, and project reminders do not override this state under any circumstances. The system transitions from an active conversational agent to an invisible observer, honoring the foundational HCI principle that the locus of control must ultimately reside with the human.

Turn-Taking, Barge-in, and Full-Duplex Dialogue

Traditional voice user interfaces operate in a rigid, half-duplex manner. In these legacy systems, the user speaks, the system processes, the system responds, and the user must wait for the system to finish before speaking again. This paradigm is fundamentally unnatural and leads to user frustration during complex tasks. Natural human conversation features overlapping speech, continuous backchanneling (such as affirming phrases like "uh-huh" or "I see"), and frequent self-repair or other-repair.

The introduction of full-duplex spoken language models fundamentally alters this interaction paradigm. Kyutai's Moshi architecture, a flagship open-source speech-to-text foundation model, processes two simultaneous audio token streams, eliminating the need for a discrete turn-taking mechanism. In a full-duplex environment, the system is essentially always listening and always generating sound, whether that sound is speech or silence. This continuous dual-stream processing allows for immediate barge-in, where the user can interrupt the system mid-sentence without causing the pipeline to crash or require a manual reset.

For the IOS-2 implementation, barge-in is a critical functional requirement, particularly during media review, sermon playback, or storyboard evaluation. When the user interrupts the system to offer a correction or an alternative idea, the voice interface must not merely halt audio playback. It must perform strict read-position reconciliation. The system must calculate exactly which audio tokens were emitted by the device speaker and theoretically processed by the user's auditory cortex prior to the interruption. By sending a truncation signal to the OpenAI Realtime API, subsequent LLM context windows accurately reflect the true state of the conversation, allowing the system to understand that the user never heard the end of the interrupted sentence.

Eyes-Free Transitions and Cognitive Load in Text Editing

During complex workflows—such as drafting media, storyboarding, or reviewing gathered context—the user will frequently need to edit text, metadata, or durable action items using voice alone. The EYEditor and EDITalk studies, presented extensively at the ACM CHI conferences, highlight the severe cognitive challenges of mobile, eyes-free text editing. These studies identified two primary user behaviors for eyes-free correction that the system must support naturally.

The first behavior is commanding, wherein the user issues explicit instructions to the system to alter the text. Examples include phrases like "Delete the last sentence" or "Change the word 'effective' to 'efficient'". The second behavior is re-dictation, also known as re-speaking. In this modality, the user simply speaks over the erroneous portion with the correct text, trusting the system to understand the syntactic replacement. For example, if the system reads back the phrase "he go there," the user might interrupt and simply say "he goes there".

Research demonstrates that while re-dictation is faster and more efficient for making longer, complex corrections, commanding is often the preferred technique for making precise, one- or two-word edits in the text. Furthermore, while re-dictation gives users a sense of perceived naturalness of use, commanding provides a necessary sense of perceived control. Smart voice agents designed for eyes-free editing significantly reduce cognitive load when they seamlessly support both modalities without requiring explicit mode switches. The IOS-2 design will adopt this dual-modality approach. If the system is reading a drafted report and the user barges in with a natural continuation or re-phrasing of the current sentence, the system interprets it as re-dictation. If the user utilizes explicit verbs, the system interprets it as commanding, modifying the durable action item on the RLM-ADK backend accordingly without requiring the user to look at the screen.

Architectural Separation of Execution and Voice Sessions

A fundamental requirement of the IOS-2 architecture is that recording, transcription, conversational voice sessions, speaking permission, and backend server work are treated as strictly independent operational tracks. A paid voice session does not need to remain open merely because continuous device recording continues.

The Financial Imperative of Decoupling

The OpenAI Realtime API converts streamed audio into billable tokens at a continuous rate. Specifically, streamed silence generates billable input tokens just as spoken words do. If the iOS application were to open a WebSocket connection to the Realtime API and leave it open during an hour of ambient silence or a silent prayer session, the system would process approximately 36,000 tokens of silence, resulting in unnecessary and substantial financial costs.

To prevent this, the native iOS client must act as an intelligent, localized gatekeeper. The AVAudioSession maintains the open microphone, continuously writing the audio data into a local, circular ring buffer on the device. Concurrently, a lightweight, on-device Voice Activity Detector or a localized speech recognition model monitors this buffer for conversational intent or specific wake phrases. The connection to the paid API is only established—or an existing dormant connection is only utilized to transmit audio—when speech directed at the system is confirmed.

Closing Sessions Without Losing Context

When a conversational turn ends and the user returns to a silent workflow, the system can gracefully close the paid WebSocket session while the local device recording continues uninterrupted. Because the iOS application manages the state, it retains the metadata regarding the user's current project. The OpenAI Realtime API supports session hydration, meaning that when the user speaks again, the iOS client can initialize a new session and inject the prior context, summary, or durable action items into the initial system prompt, allowing the conversation to resume seamlessly.

Proactive Reminders and Wake Mechanisms

This architectural decoupling ensures that wake and proactive behaviors function flawlessly without incurring the cost of transmitting hours of silence to a remote endpoint. When the RLM-ADK execution backend determines that a proactive interaction is required—such as an upcoming calendar departure or a scheduled project interview—it sends a silent push notification to the iOS client. The iOS client, operating in the background, evaluates its current state. If the state permits proactive speech, the client initiates a brief connection to the TTS engine or the Realtime API, downloads the synthesized audio, and plays it through the AVAudioSession using ducking protocols to lower the volume of any concurrent media playback. Once the proactive reminder is delivered, the client opens the listening window, ready to capture the user's response.

State Machine and Mode Design

The IOS-2 portal operates as a deterministic state machine governing the AVAudioSession and the outbound network connections. This state machine relies on explicit controls and well-defined transitions to prevent the failure modes associated with probabilistic availability inference.

Ordinary Status: Request-Driven and Proactive

In its default state, the system operates in an ambient listening mode defined as Ordinary Status. Continuous device recording runs in the background. During this state, the system is fully permitted to initiate proactive speech. This includes calendar preparation, departure warnings, and prompting the user for input on specific project phases that the RLM-ADK backend has marked as blocked or needing human review. This proactivity relies on the execution backend triggering events, but the ultimate authority to speak rests with the local iOS state machine verifying that the user is in Ordinary Status. If the user initiates a conversation, the system transitions into an active conversational voice session, processing few-minute Scripture playback, devotional readings, or natural questions.

Explicit Quiet Mode

Explicit Quiet is a user-invoked, persistent state designed to suppress all proactive system behavior. When the user issues a command such as "System, be quiet," or toggles the hardware interface, the state machine transitions immediately.

Upon entering Explicit Quiet, the connection to the conversational API is severed. All proactive speech, including critical calendar timers and departure warnings, is completely suppressed. The system logs these events visually or sends them to the backend as missed notifications, but it strictly prohibits audio output. The Quiet mode persists indefinitely until an explicit wake command—such as "System, wake up"—is detected by the local device. This design intentionally accepts the risk of a missed calendar event to avoid the catastrophic failure mode of an inferred availability system interrupting a highly sensitive real-world interaction simply because a scheduled timer triggered. Background work, such as the backend drafting a report based on previous context, continues silently.

Prayer Mode Capture

Prayer mode represents the most delicate and functionally distinct interaction state. Prayer is characterized by highly variable pacing, prolonged periods of absolute silence, weeping, or non-linguistic vocalizations. Standard voice activity detection algorithms, which typically truncate recording after two to five seconds of silence to conserve processing power, will critically fail in this context.

When the user invokes Prayer Capture, the iOS application enters a specialized recording loop. Standard endpointing algorithms and VAD timeouts are completely disabled. Silence must never end prayer. To protect against application crashes or memory exhaustion during extended sessions, the audio stream is written directly and durably to the device's local storage in chunked files. The real-time conversational API is strictly disengaged to prevent billing for infinite silence.

The mode is terminated only by explicit physical control, such as a SwiftUI button press, or a highly specific, locally recognized voice command that is difficult to trigger accidentally. Upon termination, the recorded audio artifacts are saved, securely dispatched to the backend for asynchronous batch transcription, and the system automatically transitions into the Explicit Quiet state, waiting for further explicit instruction.

Speech Engine Evaluation and Cost Modeling

The selection of the underlying speech models heavily influences the final architecture, balancing latency, naturalism, paralinguistic comprehension, and financial viability. The user-selected performance gold standard is OpenAI live voice, but alternative approaches provide critical context for the final implementation decision.

OpenAI Realtime API (The Gold Standard)

As of October 2026, OpenAI's Realtime API offers a single-model, speech-to-speech architecture capable of processing audio inputs and outputs natively. This API bypasses the traditional cascaded pipeline of converting speech to text, running a text LLM, and converting the text back to speech. By processing native audio tokens, it preserves paralinguistic data such as tone, emotion, and emphasis. The API operates over WebSocket or WebRTC connections, natively supporting function calling and session state management.

It is necessary to distinguish the current models from previous iterations. The flagship model is gpt-realtime-2.1. The terminology "GPT-Live" frequently referenced in developer forums or older documentation often points to disparate transcription services like gpt-live-transcribe, whereas the conversational endpoint is strictly defined as the Realtime API. Older beta models designated as gpt-4o-realtime-preview are being phased out in favor of the current 2.1 general availability models.

API Billing versus ChatGPT Pro Subscription:
A critical distinction must be made regarding the financial structure of these tools. ChatGPT Pro is a consumer-facing subscription billed at a flat monthly rate, providing access to the ChatGPT application interface. This subscription usage is entirely separate from API billing. The OpenAI Realtime API operates on a developer-focused, pay-as-you-go model that draws from a pre-paid credit balance. Accessing the Realtime API to build a custom iOS portal will incur usage-based charges regardless of whether the developer holds a ChatGPT Pro subscription.

Token Economics and Financial Modeling:
The Realtime API tokenizes audio at a dense, fixed rate. Input audio converts to roughly 600 tokens per minute, while output audio converts to about 1,200 tokens per minute.

gpt-realtime-2.1 (Flagship): Audio input is priced at $32.00 per 1 million tokens, and audio output is $64.00 per 1 million tokens. This equates to approximately $0.019 per minute for listening and $0.077 per minute for speaking.

gpt-realtime-2.1-mini: A faster, highly cost-effective alternative for routine support or scoped interactions. It is priced at $10.00 per 1 million audio input tokens and $20.00 per 1 million audio output tokens.

Real-world costs run higher than the base token mathematics because each conversational turn requires the model to re-process the growing context window. While OpenAI has introduced prompt caching, which reduces the cost of cached audio input to $0.40 per 1 million tokens (a 99% reduction), this caching is highly dependent on exact prefix matching. An uncached, runaway session on the flagship model can rapidly escalate to $0.46 per minute. Assuming caching works optimally, a realistic budget for a highly interactive conversational minute lands between $0.06 and $0.11 on the flagship model, and $0.02 and $0.05 on the mini model.

Open-Source Speech-to-Speech Architecture (Kyutai Moshi)

The nearest architectural alternative to the OpenAI Realtime API is Kyutai's Moshi model and its derivatives, such as NVIDIA's PersonaPlex. Released as open-source in 2024, Moshi represents a breakthrough in full-duplex spoken dialogue frameworks. Instead of relying on a turn-taking mechanism, Moshi explicitly processes the input and output audio streams jointly into two autoregressive token streams.

This architecture allows the model to always listen and always generate sound, natively supporting interruptions, overlapping speech, and backchanneling without requiring an external VAD system to gate the flow of information. Moshi boasts a theoretical latency of 160ms and a practical latency of 200ms. Because it is open-source, the per-minute API cost is eliminated. However, running a continuous, full-duplex model requires substantial persistent GPU resources (such as NVIDIA CUDA infrastructure with high VRAM availability) on the self-hosted backend, shifting the cost from a variable API expense to a fixed infrastructure overhead.

Cascaded Architecture (Cartesia Sonic and Deepgram)

A traditional cascaded architecture relies on linking independent components: a fast Speech-to-Text engine, a text-based LLM, and an ultra-fast Text-to-Speech engine. Cartesia's Sonic engine is a premier TTS option in this space, advertising a sub-90ms model time-to-first-audio. However, third-party benchmark measurements indicate that real-world streaming latency, which includes network round-trip times, medians between 166ms and 190ms.

Cartesia operates on a credit-based pricing model, with commercial access starting at the Pro tier for $5 per month. When combined with an STT engine like Deepgram Nova-3 (priced at approximately $0.0043 per minute), a cascaded stack can operate very economically, roughly between $0.02 and $0.04 per total pipeline minute.

The primary drawback of the cascaded approach is that it is strictly half-duplex. It suffers from a severe textual information bottleneck; paralinguistic metadata such as sighing, hesitation, or ambient background context is stripped during the STT phase and cannot be processed by the LLM. Furthermore, a cascaded pipeline struggles immensely with natural barge-in, as the TTS generation must be explicitly halted and the LLM reprompted when the external VAD detects a user interruption.

Read-Position Reconciliation and Eyes-Free Transitions

A defining feature of the IOS-2 conversational design is its ability to handle interruptions gracefully while maintaining an accurate understanding of what audio the user actually heard. When a user interrupts a lengthy system response—such as a scripture playback or a detailed storyboard review—the system must perform read-position reconciliation.

In the OpenAI Realtime API architecture, the server streams output tokens continuously. However, due to network buffering and local device playback buffers, the server is always slightly ahead of the audio emitting from the iPhone's speaker. If the user barges in, the local iOS client immediately detects the speech via VAD and halts the local audio playback. It then calculates the precise duration of audio that was actually played to the user. The client issues an interruption event back to the Realtime API, instructing the server to truncate the assistant's message in the conversational history at that exact token.

This reconciliation ensures that the LLM's context window accurately reflects reality. If the LLM generated a five-sentence paragraph, but the user interrupted after the second sentence, the truncated context window prevents the LLM from assuming the user heard the final three sentences. This is critical for natural testimony interviews and correction workflows, ensuring the system does not act on assumptions derived from unplayed audio.

Long research and creative requests generated during voice sessions become durable action items and produce actual reviewable outputs after the voice session ends. Theographic Schema vs. Temporal Extraction Frameworks

The system relies on a diverse array of existing source products, including prayer transcripts, sermon text, YouTube metadata, and Scripture references. Because there is no single consolidated knowledge backend, the architecture must utilize specialized schemas for distinct data types while maintaining strict source identities, revisions, and evidence citations.

For biblical datasets, the Theographic schema provides a robust, deterministic candidate. Theographic operates as a highly structured knowledge graph, explicitly weaving together data about biblical people, places, periods, and passages. When a creative workflow involves Scripture reference or sermon drafting, the RLM-ADK backend maps the conversational entities against the static Theographic schema to ensure theological and geographical accuracy.

This static mapping is fundamentally distinct from dynamic temporal extraction frameworks like Microsoft GraphRAG. GraphRAG enhances traditional retrieval pipelines by constructing dynamic knowledge graphs from arbitrary, unstructured text—such as years of personal prayer transcripts or contextual journaling. GraphRAG extracts entities, relationships, and claims, building community summaries that allow the system to trace temporal provenance. For example, if a user asks, "How has my understanding of grace evolved over the past two years of prayer captures?", the GraphRAG implementation traverses the temporal relationships extracted from the personal source documents to synthesize a grounded answer.

By utilizing Theographic for immutable biblical metadata and GraphRAG for dynamic personal context extraction, the execution backend can supply the OpenAI Realtime session with highly accurate, cited context, allowing the LLM to function as a synthesizer rather than a primary database.

iOS Native Audio Constraints and Application Lifecycle

The native workspace, designated as RawleySM/rlm-adk-ios, must navigate the strict foreground and background application lifecycles imposed by Apple's iOS. Even though an Apple Developer Program membership allows for device deployment, paid membership does not remove fundamental OS audio and memory constraints.

AVAudioSession Configuration Mechanics

To achieve continuous background recording and playback, the application must configure its Info.plist with the UIBackgroundModes key, specifically enabling the audio ("Audio, AirPlay, and Picture in Picture") entitlement. Without this entitlement, iOS will aggressively suspend the application shortly after the user locks the screen or switches to another app.

The core of the audio architecture relies on the AVAudioSession system singleton. The application must initialize the session using the AVAudioSessionCategoryPlayAndRecord category. This specific category authorizes the application to simultaneously capture microphone input and deliver audio output, which is non-negotiable for a conversational voice portal.

Crucially, the iOS application must not behave as a monolithic audio hijacker. The session must be configured with AVAudioSessionCategoryOptionMixWithOthers and ducking options. This instructs the operating system to mix the IOS-2 application's background recording and potential proactive speech over the user's concurrent media playback (such as an audiobook or music application), rather than forcibly interrupting and silencing the user's other applications.

Resolving Hardware Interruptions and Route Changes

The mobile nature of the iPhone introduces constant hardware state changes. The user may connect Bluetooth headphones, enter a car with CarPlay, or receive a cellular phone call. The iOS portal must handle these route changes gracefully without corrupting an active Prayer Capture or dropping a live API session.

The AVAudioSession broadcasts route change notifications whenever the hardware configuration shifts. The app must observe these notifications to dynamically switch input and output nodes on the AVAudioEngine. Furthermore, if the system experiences a hard audio interruption, such as an incoming cellular phone call or a Siri invocation, the AVAudioSession will temporarily deactivate. The iOS application must trap the AVAudioSessionInterruptionNotification, gracefully pause the local ring buffer, save the current file chunk, and attempt to reactivate the session and resume recording immediately upon receiving the end-interruption event. Failure to handle these lifecycle events will result in a silently failed background application.
