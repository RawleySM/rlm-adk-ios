Background Audio and Interruption Tolerance

By default, an iOS application suspends all operations shortly after being backgrounded by the user. To sustain the continuous recording and background work pipeline, the application's AVAudioSession must be configured with the AVAudioSession.Category.playAndRecord category. However, this designation alone is insufficient for a continuous background agent.

If the application attempts to initiate or maintain an audio session while backgrounded without appropriate mixability flags, the operating system will forcefully terminate the session. This termination frequently surfaces as error code 560557684 (AVAudioSessionErrorCodeCannotInterruptOthers, translated internally to the four-character code !int). This occurs because background applications are strictly prohibited from interrupting the foreground application's audio session.

To circumvent this limitation and preserve the existing safeguards without resorting to hypothetical or unsupported security-hardening architectures, the SwiftUI lifecycle must configure the audio session with two highly specific options:

AVAudioSessionCategoryOptionMixWithOthers: This explicitly allows the portal's audio session to coexist with other applications playing audio. Setting this flag is mandatory for background execution.

AVAudioSessionCategoryOptionDuckOthers: This optional but highly recommended setting automatically reduces the volume of background audio (e.g., Spotify, Apple Music, or YouTube) when the agent initiates a proactive spoken transition. It returns the background media to normal volume once the AVAudioSession finishes its output.

Implementing Quiet and Prayer Capture States

The product design specifies that ordinary background work continues, but "Quiet" mode suppresses all speech until an explicit wake, and "Prayer" capture tolerates long silences, ending only by explicit control. Calendar timers do not override the Quiet mode.

Because the OpenAI Realtime server_vad triggers automatically after silence_duration_ms (typically defaulting to 500-600 milliseconds), it is structurally incompatible with Prayer mode, which intrinsically necessitates long silences for contemplation.

To resolve this architectural conflict, the iOS client must assume absolute authority over Voice Activity Detection (Client-Side VAD). During Prayer mode, the client sets the Realtime API turn_detection to null via a session.update payload. The client continues to stream input_audio_buffer.append events, but the backend will not interrupt the user regardless of the length of the silence. Once the user explicitly concludes the prayer, the client sends an input_audio_buffer.commit event followed immediately by a conversation.item.create event. This sequence prompts the backend to process the entire buffered sequence, outputting the complete whisper-1 transcript to the durable source database for subsequent analysis or storage.

During Quiet mode, the microphone buffer loop runs entirely locally, utilizing a lightweight on-device energy threshold or push-to-talk mechanism. Until the explicit wake is triggered, no input_audio_buffer.append events are transmitted to the OpenAI websocket. This hybrid local/cloud gating mechanism preserves substantial API costs while ensuring the portal is instantly available when required.

Measured Evidence: The Risks of Autonomous Extraction

Despite the robust publisher claims, independent evaluation of Graphiti reveals significant operational risks for a production deployment, particularly concerning the validation burden and operating costs.

Collateral Invalidation: Because Graphiti relies on an LLM to autonomously determine which old edges to invalidate, it frequently closes the validity windows of completely unrelated facts. An independent audit of a production graph documented in Caura AI's architectural review (and verified against Graphiti's GitHub Issue #1728) found that 1,616 of 3,950 facts (41%) were marked invalid_at erroneously. Saving a memory that merely mentioned an entity often retired an unrelated fact about it because edge invalidation searched the whole graph.

LLM Extraction Costs and Latency: The add_episode command requires multiple sequential LLM calls to extract entities, resolve deduplication, extract edges, and invalidate existing facts against the graph. Users report single-sentence episodes taking upward of 600 seconds on rate-limited endpoints, with cost estimates reaching $0.80 for 40 short interactions using default OpenAI models.

Database Indexing Failures: The framework relies on underlying graph databases such as Neo4j or FalkorDB. Users have reported severe backend-specific search issues, including unindexed UUID equality scans causing broad timeouts and complete system stalls during add_episode execution at scale (GitHub Issues #1272, #1592, #1819).

MCP Server Token Inflation: Teams wiring Graphiti's Model Context Protocol (MCP) server into workflows report that the server routinely returns raw fact_embedding arrays directly to the model, artificially inflating token consumption by up to 50 times (GitHub Issue #610).

For the BACKEND-3 architecture, where exact source identity, precise reconstructible citations, and specific correction tracking are required—and where "clinical findings" extraction is rejected in favor of a user-defined vocabulary—the autonomous, probabilistic extraction of Graphiti introduces unacceptable entropy.

Alternatives: Mem0, Letta, and Microsoft GraphRAG

It is necessary to contrast Graphiti with alternative semantic memory layers.

Mem0 utilizes a two-phase pipeline (extract and reconcile) with a focus on token efficiency. It extracts candidate facts from each message pair and reconciles them against existing memory (arXiv:2504.19413, published April 2025). However, it updates memories by replacing them or appending them semantically, lacking a strict mathematical bi-temporal structure.

Letta provides a tiered operating-system-like memory (Core, Recall, Archival) managed entirely by the agent through tool calls. The agent explicitly writes to memory blocks.

Microsoft GraphRAG (arXiv:2404.16130) focuses on document corpus ingestion and hierarchical community summarization for global sensemaking, rather than incremental, transaction-time agent memory. In temporal reasoning benchmarks (arXiv:2607.05577), standard GraphRAG achieved only 18.8% accuracy compared to Graphiti's 57.4%.

While Mem0 and Letta excel in standard conversational agent contexts, neither provides the rigorous chronological guarantees required to ensure that prayer text corrections do not advance listing timestamps, or that exact source revisions can be targeted for late repairs via a synchronization cursor.

Relational Bitemporal Schema: PostgreSQL & SQL:2011

To satisfy the stringent requirements for temporal knowledge, source provenance, and exact correction tracking, the architecture must abandon probabilistic LLM graph management in favor of a highly deterministic bitemporal relational schema, natively supported by PostgreSQL.

System Time versus Business Time

The SQL:2011 standard formalized the concept of bi-temporal tables, establishing two distinct axes of time:

Business Time (Valid Time / Event Time): The period during which a fact is true in the real world (e.g., the exact duration of a calendar event, or the time a prayer was spoken).

System Time (Transaction Time / Observation Time): The exact database timestamp when the system recorded, updated, or deleted the fact.

In the BACKEND-3 ecosystem, the supplied contracts demand that corrections to prayer text may not advance the listing timestamps. This requires strict separation of these temporal axes. When a user edits a transcript from a week ago, the Business Time remains anchored in the past, but the System Time advances to the current transaction instant (now()). Consumer clients querying the UI sort by Business Time, ensuring the listing order does not change. Conversely, consumer clients syncing local states query by System Time to pull the delta.

Schema Implementation via PostgreSQL Range Types

PostgreSQL achieves rigorous SQL:2011 bitemporal compliance using timestamp range types (specifically tstzrange) and GiST (Generalized Search Tree) exclusion constraints.

A generic schema for context source tables (capturing prayer transcripts, teaching texts, and metadata) is defined to prevent overlapping valid timelines for a single entity, employing the WITHOUT OVERLAPS constraint paradigm:

SQL
-- Enable GiST indexing for exclusion constraints
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE context_sources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_type TEXT NOT NULL,           -- e.g., 'prayer', 'sermon', 'scripture'
    digest TEXT NOT NULL,                -- Cryptographic hash for consumer comparison
    content TEXT NOT NULL,
    metadata JSONB,
    valid_range TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),
    sys_period TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),

    -- Ensure no overlapping valid_range for the same ID
    EXCLUDE USING GIST (
        id WITH =,
        valid_range WITH &&
    )
);


The GiST exclusion constraint (valid_range WITH &&) mathematically guarantees that no two records for the same id can have overlapping valid_range windows.

If a transcript or contextual record is corrected, the database executes a temporal split:

The old record's sys_period is closed (the upper bound is set to the transaction time, now()).

A new record is inserted with the corrected content, generating a new digest. Its valid_range exactly matches the original event time, but its sys_period starts at now().

This architecture satisfies the requirement that design updates, removals, and superseded claims are entirely reconstructible. It maintains absolute fidelity to the exact source history without relying on an LLM to probabilistically manage edge invalidation, eliminating the risk of collateral invalidation entirely.

Change Cursor Semantics and Test Matrix

A defining feature of this architecture is the necessity to support "late repairs" across decentralized consumer endpoints without breaking chronological flow or UI sorting logic.

Adapter and Cursor Semantics

A simple sequence ID or a traditional updated_at column fails catastrophically for temporal data. An updated_at mutation violates the principle of immutability, and a sequential ID does not cleanly map to point-in-time historical reconstruction.

The change cursor must iterate strictly over the Transaction Time (sys_period), not the Event Time (valid_range).

When a downstream consumer requests a delta sync for late repairs or updates:

Request: The client issues GET /sync?cursor=2026-10-10T12:00:00Z.

Query: The adapter translates this to SELECT * FROM context_sources WHERE lower(sys_period) >= '2026-10-10T12:00:00Z'.

Response: The server returns all records (insertions, supersessions, and deletions) that the database observed since the cursor timestamp.

Because a deletion or an update in a bitemporal system is merely the insertion of a new row with a closed valid_range or sys_period upper bound, the consumer naturally receives the "tombstone" or the updated state, advancing its local cursor to the maximum lower(sys_period) received in the batch.

This prompts the backend to process the entire buffered sequence as a single monolithic block, outputting the complete whisper-1 transcript to the durable source database and allowing the session to terminate gracefully.

During Quiet mode, the architecture takes a more aggressive approach to cost savings. The microphone buffer loop runs entirely locally, utilizing a lightweight on-device wake-word or push-to-talk mechanism. Until the explicit wake is triggered, no input_audio_buffer.append events are transmitted to the OpenAI websocket, preserving substantial API costs while adhering to the requirement that background work continues.

Proactive Speech and Spoken Transitions

Outside of the Quiet and Prayer states, the system is designed to initiate proactive speech covering calendar preparation, departure sequences, and project phases requiring input. Because ordinary status relies on the user's request, the proactive engine must bridge the gap between background data gathering and live conversational sessions.

When the background execution layer detects a proactive trigger (e.g., a calendar departure event approaching), it establishes the WebSocket connection and immediately dispatches a conversation.item.create event populated with the contextual prompt, followed by a response.create command. This forces the agent to speak first, delivering the necessary information to the user through the iOS audio session, which ducks any active background music. Long research and creative requests, which become durable action items producing actual reviewable outputs (websites, books, reports), are processed entirely out-of-band. Once the voice session ends, the execution backend continues the generative workflows asynchronously, eventually notifying the user through a subsequent proactive speech event or a native UI update.

Temporal Knowledge Graph Evaluation: Graphiti, Mem0, and Letta

The personal context backend relies fundamentally on the temporal ordering of facts. For example, a user's prayer concerns, active projects, and daily metadata evolve continuously. Traditional Retrieval-Augmented Generation (RAG) models rely on static vector stores that retrieve information based solely on semantic similarity. These systems either destructively overwrite old information or accumulate contradictory statements, leading to catastrophic context degradation and hallucination over long horizons. The architectural review mandates a deep comparative analysis of temporal memory frameworks, specifically examining Graphiti against alternatives like Mem0 and Letta.

Measured Evidence and Autonomous Vulnerabilities

Despite the theoretical elegance of the Graphiti model, independent evaluation reveals significant operational vulnerabilities that disqualify it for the precise requirements of the BACKEND-3 environment.

The primary vulnerability is "collateral invalidation." Because Graphiti relies on an LLM to autonomously determine which historical edges to invalidate, it frequently closes the validity windows of entirely unrelated facts. An audit of a production Graphiti deployment reported that out of 3,950 facts, 1,616 (41%) were erroneously marked with an invalid_at timestamp. A manual review demonstrated that saving a memory that merely mentioned an entity often prompted the LLM to retire an unrelated but valid fact about that same entity. For a personal context portal managing exact prayer text corrections and scripture citations, this autonomous entropy is unacceptable.

Furthermore, the ingestion pipeline imposes severe latency and cost penalties. The add_episode command requires multiple sequential LLM calls to extract entities, resolve deduplication, extract new edges, and query the existing graph for invalidation candidates. Users report that a single-sentence episode can take upward of 600 seconds on rate-limited endpoints, with cost estimates reaching $0.80 for 40 short interactions. Finally, the framework relies on underlying graph databases (such as Neo4j or FalkorDB), and users have documented unindexed UUID equality scans causing broad timeouts and complete system stalls during edge extraction at scale.

Contrasting Alternatives: Mem0 and Letta

It is necessary to contrast Graphiti with alternative semantic and tiered memory architectures to ensure no viable open-source option is overlooked.

Mem0 utilizes a two-phase pipeline focused heavily on token efficiency and semantic extraction (arXiv:2504.19413). It extracts candidate facts from conversational streams and reconciles them against existing memory using vector similarity. However, Mem0 fundamentally updates memories by replacing them or appending overrides, lacking a strict mathematical bi-temporal structure. It operates more as a highly optimized semantic filter rather than an auditable temporal ledger.

Letta (formerly MemGPT) approaches memory as a tiered operating system. It provides Core, Recall, and Archival memory tiers, leaving the management of these tiers entirely up to the agent through autonomous tool calls. While highly flexible, it shifts the burden of temporal consistency to the prompt engineering layer, providing zero guarantees regarding chronological auditing, source provenance, or exact late repairs. Neither Mem0 nor Letta provides the rigorous chronological guarantees required for auditable source provenance in the BACKEND-3 environment.

Relational Temporal Design: SQL:2011 Bitemporal Schema

To satisfy the stringent requirements for temporal personal knowledge, exact source provenance, and deterministic correction tracking, the architecture must abandon probabilistic graph management. The optimal solution is a strict bitemporal relational schema natively supported by PostgreSQL, leveraging the SQL:2011 standard principles.

Separation of Event Time and Observation Time

The foundation of the SQL:2011 temporal standard is the absolute separation of two distinct timelines, allowing a system to record when a fact was true in the real world separately from when the database learned about it.

The first timeline is Business Time (or Event Time / Valid Time). This defines the period during which a fact is true in the modeled domain. For example, the exact duration of a calendar event, or the chronological timestamp when a prayer was originally spoken into the device.

The second timeline is System Time (or Transaction Time / Observation Time). This records the exact machine timestamp when the database stored or updated the fact. It is maintained strictly by the database engine and cannot be manipulated by the application layer.

This separation elegantly solves the core supplied contract: prayer text corrections must not advance listing timestamps. When a user edits a transcript from three days ago to fix a transcription error, the Business Time remains anchored in the past, entirely unchanged. However, the System Time is closed on the old record, and a new record is inserted with a System Time beginning at now(). Consumer clients querying the user interface sort exclusively by Business Time, ensuring the listing order does not change. Simultaneously, background sync engines query by System Time to pull the delta, ensuring the correction is propagated without a full database sweep.

Schema Implementation via PostgreSQL Range Types

PostgreSQL achieves rigorous SQL:2011 bitemporal compliance natively using timestamp range types (tstzrange) and GiST (Generalized Search Tree) exclusion constraints.

The architecture defines a context source table designed to prevent overlapping valid timelines for any single entity using the WITHOUT OVERLAPS paradigm. The following schema provides the concrete interface for the BACKEND-3 environment:

SQL
-- Ensure the GiST extension is available
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- Define the bitemporal source table
CREATE TABLE context_sources (
    id UUID DEFAULT gen_random_uuid(),
    source_type TEXT NOT NULL,
    digest TEXT NOT NULL,
    content TEXT NOT NULL,
    metadata JSONB,

    -- Business Time (Event Time)
    valid_range TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),

    -- System Time (Observation Time)
    sys_period TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),

    -- Primary bitemporal key ensuring no overlapping realities
    EXCLUDE USING GIST (
        id WITH =,
        valid_range WITH &&
    )
);


The GiST exclusion constraint (valid_range WITH &&) is the mathematical engine of the architecture. It guarantees that no two records sharing the same id can have overlapping valid_range windows.

If a transcript is corrected, the database executes a deterministic temporal split. The old record's sys_period is updated, closing its upper bound to now(). Simultaneously, a new record is inserted with the corrected content, generating a new cryptographic digest. The new record inherits the original valid_range (the event time), but its sys_period starts exactly at now(). This paradigm ensures that all updates, removals, and superseded claims are entirely reconstructible, maintaining absolute fidelity to the source history without relying on an LLM to manage edge invalidation.

Source Provenance and Theographic Domain Projections

The BACKEND-3 domain projection relies on independent source pipelines. These source classes include prayer transcripts, teaching texts, scripture references, calendar data, and other personal-context records. The architecture strictly dictates that there is no selected consolidated knowledge backend; instead, the bitemporal PostgreSQL store acts as an immutable, generalized ledger from which consuming projects project their own domain-specific ontologies.

Mapping the Theographic Schema to Personal Context

Scripture references and personal context sources must retain their source edition and digest-qualified locators. The target schema candidate for biblical data is Theographic, an open-source, CC BY-SA 4.0 metadata dataset.

The Theographic dataset normalizes biblical metadata into distinct, highly structured entity classes:

People: Biblical figures, including complex alias mapping (e.g., Saul and Paul).

Places: Geographic bounding points and historical regions.

Events: Temporal occurrences connected to specific narratives.

Passages: Digest-qualified locators denoting the exact book, chapter, verse, and translation edition (e.g., Genesis 1:1, BSB translation).

This dataset provides a pristine, generic schema example that avoids the pitfalls of tracking parts vocabulary as clinical findings. When the OpenAI Realtime agent processes a conversational workflow—such as a user reflecting on a specific sermon discussing King David—the backend does not simply dump semantic text into a vector database. Instead, the agent executes an explicit tool call to extract the entities and maps them directly to the Theographic schema.

Reconstructible Citations and Digest Comparisons

The user contract mandates that consumers compare text digests and membership. Because the bitemporal table stores a cryptographic hash (digest) of the content payload, downstream consumers (such as an iPad application, a separate website renderer, or a localized vector cache) can synchronize efficiently without downloading the entire payload blindly.

If a source text is updated via a late repair, the digest inherently changes. The consumer application checks its local digest against the server's digest for a given id. If they differ, the consumer fetches the updated payload. Crucially, Scripture text citations retain their source edition by storing the translation metadata (e.g., "BSB", "WEB") directly in the immutable JSONB metadata column. This prevents the LLM from inadvertently summarizing or hallucinating the text version, ensuring the citation remains perfectly reconstructible across all domain projections.

Adapter and Cursor Semantics for Late Repairs

A defining feature of the BACKEND-3 architecture is the requirement to support "late repairs" across decentralized consumer endpoints without breaking the chronological flow of the interface or requiring full-table rescans.

The Delta Sync Architecture

A simple sequential ID or a traditional updated_at timestamp column fundamentally fails for temporal data. An updated_at mutation violates the principle of immutability, permanently destroying the previous state of the row. Furthermore, a sequential ID does not cleanly map to point-in-time historical reconstruction across distributed systems.

Therefore, the change cursor must iterate exclusively over the System Time (sys_period / Observation time), not the Event Time (valid_range).

When a downstream consumer requests a delta synchronization, the adapter semantic flow operates as follows:

Client Request: The client asks for all changes since its last known observation time: GET /sync?cursor=2026-10-10T12:00:00Z

Server Query: The backend queries the bitemporal table based on the lower bound of the sys_period: SELECT * FROM context_sources WHERE lower(sys_period) >= '2026-10-10T12:00:00Z'

Server Response: The server returns all records that the database observed since the cursor timestamp, including new insertions, corrections (supersessions), and deletions.

Because a deletion or update in a strict bitemporal system is merely the insertion of a new row with a closed valid_range or sys_period upper bound, the consumer naturally receives the "tombstone" or the updated state. The client applies these changes locally and advances its local cursor to the maximum lower(sys_period) received in the batch.

Primary Source Documentation and Validation

The recommendations synthesized in this report are grounded in primary technical documentation, peer-reviewed architectures, and observed production behaviors. The following analysis integrates the evaluation of these primary sources, highlighting how they shape the architectural decisions.

The foundational paper detailing autonomous bi-temporal graphs, Zep: A Temporal Knowledge Graph Architecture for Agent Memory (arXiv:2501.13956), alongside the getzep/graphiti repository, provides the theoretical basis for the 4-timestamp model. While the paper demonstrates the superiority of graphs over static vector stores for evolving agents, third-party audits of Graphiti’s GitHub issues (specifically analyzing Issue #1728) reveal the critical flaw of collateral invalidation and severe LLM cost overheads. This observed evidence directly motivated the pivot to a relational bitemporal ledger.

The implementation mechanics for that relational ledger rely heavily on IBM and PostgreSQL literature regarding the SQL:2011 standard. Technical breakdowns of tstzrange and GiST indexes physically demonstrate how to implement bitemporal rules without locking the database into proprietary graph engines. User reports confirm the high efficacy of this architecture in production-scale systems, particularly in managing complex temporal states like domain name portfolios.

For the conversational execution layer, official specifications from the Microsoft Azure and OpenAI Realtime API documentation dictate the WebSocket protocol mechanics. These sources confirm the pcm16 24kHz audio requirement, the exact structure of the session.update payload, and crucially, the necessity of the input_audio_transcription object required to bind the whisper-1 model for out-of-band transcripts.

Finally, the constraints governing the iOS native workspace are derived directly from Apple's AVAudioSession developer documentation and historical engineering triage. This literature documents the absolute OS-level requirement to utilize AVAudioSessionCategoryOptionMixWithOthers and AVAudioSessionCategoryOptionDuckOthers to prevent background session termination (error 560557684) during continuous recording loops.

Unresolved Facts and Unknowns

While the architecture is well-defined theoretically, several constraints remain unmeasured:

Apple OS Absolute Memory and Thermal Constraints: While the required AVAudioSession flags permit background audio structurally, iOS aggressively terminates background applications under memory pressure or thermal throttling. The exact uptime of a continuous buffer stream on a physical iPhone over a 24-hour cycle remains an unknown risk and is highly dependent on the specific hardware generation (e.g., iPhone 15 Pro vs. iPhone 12).

OpenAI WebSocket Cellular Stability: The OpenAI Realtime API requires a persistent wss:// connection during active conversational phases. Disconnections due to cellular handoffs or tunnel traversal will violently sever the session. The latency penalty and state-recovery burden of re-establishing the session, re-authenticating, and re-injecting the conversational context via conversation.item.create is currently unmeasured and may require aggressive local caching.

Hardware VAD Capability: Because continuous streaming to OpenAI is economically unviable, the iOS client must run a local Voice Activity Detection algorithm to gate the transmission of audio during Quiet mode. If this on-device VAD processing exceeds the background CPU limits imposed by iOS, the application may be forcefully suspended by the system watchdog, rendering the quiet mode architecturally unstable.
