BACKEND-3 Personal temporal context and source correction architecture

Executive Recommendation

The architectural evaluation for the BACKEND-3 personal temporal context and source correction environment yields a bifurcated recommendation. The conversational voice execution layer must be built directly on the OpenAI Realtime API utilizing the WebSocket protocol to meet the specified performance standard. However, the temporal knowledge graph layer should firmly reject autonomous, model-extracted graph frameworks like Graphiti in favor of a deterministic PostgreSQL SQL:2011 bitemporal relational schema.

While publisher literature positions Graphiti as the state of the art in autonomous bi-temporal graph construction for large language models (LLMs), measured evidence from production implementations indicates critical operational friction. Specifically, Graphiti suffers from a phenomenon termed "collateral invalidation," where unrelated facts are erroneously marked as superseded due to probabilistic LLM extraction errors. For a single-user native iOS portal where deterministic source correction, exact scripture locators, and late repair cursors are foundational, a bitemporal relational design using PostgreSQL's tstzrange and GiST exclusion constraints provides the requisite, uncompromising data integrity.  

Furthermore, the native SwiftUI client must leverage AVAudioSessionCategoryPlayAndRecord combined strictly with AVAudioSessionCategoryOptionMixWithOthers and AVAudioSessionCategoryOptionDuckOthers to sustain the continuous background audio constraints mandated by the system requirements. Voice interaction must be treated as a continuous stream where local device modes—specifically "Quiet" and "Prayer capture"—dictate the client-side rendering and voice activity detection (VAD) commits, rather than severing the underlying server connection. The following report details the technical justification, comparative analysis, exact schemas, and concrete interfaces required to fulfill the BACKEND-3 requirements.  

Foundational Voice Architecture: The OpenAI Realtime Standard

Voice serves as the foundational interaction paradigm for the BACKEND-3 environment. The stated standard for this architecture is the OpenAI live voice experience, which is technically delivered to developers via the OpenAI Realtime API. It is necessary to first distinguish between the consumer-facing ChatGPT application and the developer API infrastructure.

API Identification and Economic Realities

The ChatGPT Pro subscription (currently billed at premium tiers for consumer usage) provides high-tier access to the consumer features of OpenAI's chat application. However, ChatGPT Pro subscription usage and API billing are strictly separate entities. A ChatGPT Pro subscription does not provide backend API credits, nor does it allow programmatic access to the underlying low-latency speech-to-speech architecture. The Realtime API is billed entirely on a usage basis through the OpenAI developer platform.  

The target experience identified from official documentation is powered by the gpt-4o-realtime-preview model. Multiple model snapshots exist, with versions officially designated as gpt-4o-realtime-preview-2024-10-01 and gpt-4o-realtime-preview-2024-12-17. Cost significantly influences the final choice, and the economics of the Realtime API are substantially higher than standard text-based LLM interactions. Because the BACKEND-3 portal captures continuous device recording—including explicit quiet periods and long prayer modes—transmitting raw, unbroken audio directly to the API on a continuous 24-hour basis would incur prohibitive, unsustainable costs. Therefore, the architecture must strictly decouple continuous on-device recording from active Realtime API streaming sessions. A hybrid approach is mandatory: local on-device processing must gate the audio stream, only opening the WebSocket connection or transmitting buffers to the cloud provider when explicit wake conditions, proactive calendar notifications, or project phases necessitate input.

WebSocket Protocol and Session Configuration

The Realtime API operates over a persistent, full-duplex WebSocket connection (wss://). The conversational session must be configured immediately upon connection using the session.update payload. To achieve the lowest latency and highest fidelity, the API expects raw uncompressed audio. The iOS client must capture and transmit audio using the pcm16 format at a 24kHz sample rate (mono).  

The session.update event allows the backend to inject system instructions and define the exact audio footprint. The client continuously sends input_audio_buffer.append events containing base64-encoded PCM audio chunks.  

JSON
{
  "type": "session.update",
  "session": {
    "voice": "alloy",
    "instructions": "System instructions for BACKEND-3 context.",
    "input_audio_format": "pcm16",
    "output_audio_format": "pcm16",
    "turn_detection": {
      "type": "server_vad",
      "threshold": 0.4,
      "silence_duration_ms": 600
    },
    "input_audio_transcription": {
      "model": "whisper-1"
    }
  }
}

The system relies entirely on an event-driven loop. By default, the API utilizes a server-side Voice Activity Detection (server_vad) mechanism. The server monitors the appended buffers, detects speech start (input_audio_buffer.speech_started), and automatically commits the buffer upon detecting silence (input_audio_buffer.speech_stopped), subsequently generating a response.  

Out-of-Band Transcription for Source Products

A core requirement of the BACKEND-3 architecture is generating precise transcripts of user interactions to serve as durable source products (e.g., prayer transcripts, research queries, and creative workflow context). The gpt-4o-realtime-preview model excels at generating low-latency speech-to-speech responses but does not natively return a reliable textual transcript of the user's audio input in its standard event flow.

To fulfill this requirement, the session must enable out-of-band transcription by supplying an input_audio_transcription object within the initial session.update event, explicitly specifying the whisper-1 model. When this parameter is successfully registered, the server dispatches a conversation.item.input_audio_transcription.completed event alongside the audio response, providing a highly accurate text digest of the user's conversational turn. It is critical to note from measured implementation evidence that if input_audio_transcription is omitted from the initial session configuration, the developer must send a subsequent session.update to pin the transcription model, as omitting it results in total silence from the transcription subsystem. Furthermore, background noise can cause discrepancies between the Realtime model's audio interpretation and the whisper-1 transcript, necessitating careful client-side audio preprocessing.  

Native Workspace Constraints: iOS Audio Session Management

The execution layer exists within a native SwiftUI iPhone portal, utilizing the RawleySM/rlm-adk-ios workspace. Because continuous recording is mandated—including states where the screen is locked, the application is backgrounded, or the user is utilizing other media applications—the integration with the host operating system's AVAudioSession is critical to the stability of the entire architecture.

It is a documented reality of the Apple ecosystem that paid membership in the Apple Developer Program does not exempt an application from strict OS-level audio constraints. The application must operate entirely within the bounds of standard iOS background execution protocols.

Background Audio and Interruption Tolerance

By default, an iOS application suspends all operations shortly after being backgrounded by the user. To sustain the continuous recording and background work pipeline, the application's AVAudioSession must be configured with the AVAudioSession.Category.playAndRecord category. However, this designation alone is insufficient for a continuous background agent.  

If the application attempts to initiate or maintain an audio session while backgrounded without appropriate mixability flags, the operating system will forcefully terminate the session. This termination frequently surfaces as error code 560557684 (AVAudioSessionErrorCodeCannotInterruptOthers, translated internally to the four-character code !int). This occurs because background applications are strictly prohibited from interrupting the foreground application's audio session.  

To circumvent this limitation and preserve the existing safeguards without resorting to hypothetical or unsupported security-hardening architectures, the SwiftUI lifecycle must configure the audio session with two highly specific options:

  1. AVAudioSessionCategoryOptionMixWithOthers: This explicitly allows the portal's audio session to coexist with other applications playing audio. Setting this flag is mandatory for background execution.  

  2. AVAudioSessionCategoryOptionDuckOthers: This optional but highly recommended setting automatically reduces the volume of background audio (e.g., Spotify, Apple Music, or YouTube) when the agent initiates a proactive spoken transition. It returns the background media to normal volume once the AVAudioSession finishes its output.  

Implementing Quiet and Prayer Capture States

The product design specifies that ordinary background work continues, but "Quiet" mode suppresses all speech until an explicit wake, and "Prayer" capture tolerates long silences, ending only by explicit control. Calendar timers do not override the Quiet mode.

Because the OpenAI Realtime server_vad triggers automatically after silence_duration_ms (typically defaulting to 500-600 milliseconds), it is structurally incompatible with Prayer mode, which intrinsically necessitates long silences for contemplation.  

To resolve this architectural conflict, the iOS client must assume absolute authority over Voice Activity Detection (Client-Side VAD). During Prayer mode, the client sets the Realtime API turn_detection to null via a session.update payload. The client continues to stream input_audio_buffer.append events, but the backend will not interrupt the user regardless of the length of the silence. Once the user explicitly concludes the prayer, the client sends an input_audio_buffer.commit event followed immediately by a conversation.item.create event. This sequence prompts the backend to process the entire buffered sequence, outputting the complete whisper-1 transcript to the durable source database for subsequent analysis or storage.  

During Quiet mode, the microphone buffer loop runs entirely locally, utilizing a lightweight on-device energy threshold or push-to-talk mechanism. Until the explicit wake is triggered, no input_audio_buffer.append events are transmitted to the OpenAI websocket. This hybrid local/cloud gating mechanism preserves substantial API costs while ensuring the portal is instantly available when required.

Evaluation of Temporal Knowledge Graph Architectures

The independent research angle mandates a rigorous focus on temporal personal knowledge, source provenance, and correction. The personal context backend relies heavily on the temporal ordering of facts. For example, a user's prayer concerns, active projects, daily metadata, and changing reflections evolve constantly. Traditional Retrieval-Augmented Generation (RAG) paradigms rely on static vector stores, which either destructively overwrite old information or indiscriminately accumulate contradictory statements, leading to agent hallucination.  

The industry has proposed several graph-based memory frameworks to solve this, most notably Graphiti (the open-source core of Zep), Mem0, Letta, and Microsoft GraphRAG.

Graphiti: Autonomous Bi-Temporal Graphs

Zep’s open-source framework, Graphiti, implements a bi-temporal knowledge graph architecture documented extensively in a January 2025 paper (arXiv:2501.13956). Graphiti models knowledge as a graph G=(N,E,ϕ)\mathcal{G} = (\mathcal{N}, \mathcal{E}, \phi)G=(N,E,ϕ) where entities (nodes) are connected by facts (edges), and ϕ\phiϕ represents the incidence function.  

Crucially, Graphiti maintains four timestamps for every fact:

  • tvalidt_{valid}tvalid​: When the fact became true in the real world (Business Time).

  • tinvalidt_{invalid}tinvalid​: When the fact was superseded.

  • tcreated′t'_{created}tcreated′​: System ingestion time (Transaction Time).

  • texpired′t'_{expired}texpired′​: System removal time.  

In this model, when an LLM extracts a new episode (e.g., a conversation where the user states, "I finished the backend project"), Graphiti identifies the existing entity, detects the contradicting previous edge ("I am working on the backend project"), and updates the old edge's tinvalidt_{invalid}tinvalid​ timestamp. It closes the validity window rather than deleting the fact, thereby preserving the provenance of the correction. This theoretically allows point-in-time reasoning: "What was true on October 1st?".  

Publisher claims state that using gpt-4o, Zep achieved an 18.5% accuracy improvement over baseline implementations on enterprise-critical tasks like cross-session information synthesis.  

Measured Evidence: The Risks of Autonomous Extraction

Despite the robust publisher claims, independent evaluation of Graphiti reveals significant operational risks for a production deployment, particularly concerning the validation burden and operating costs.

  1. Collateral Invalidation: Because Graphiti relies on an LLM to autonomously determine which old edges to invalidate, it frequently closes the validity windows of completely unrelated facts. An independent audit of a production graph documented in Caura AI's architectural review (and verified against Graphiti's GitHub Issue #1728) found that 1,616 of 3,950 facts (41%) were marked invalid_at erroneously. Saving a memory that merely mentioned an entity often retired an unrelated fact about it because edge invalidation searched the whole graph.  

  2. LLM Extraction Costs and Latency: The add_episode command requires multiple sequential LLM calls to extract entities, resolve deduplication, extract edges, and invalidate existing facts against the graph. Users report single-sentence episodes taking upward of 600 seconds on rate-limited endpoints, with cost estimates reaching $0.80 for 40 short interactions using default OpenAI models.  

  3. Database Indexing Failures: The framework relies on underlying graph databases such as Neo4j or FalkorDB. Users have reported severe backend-specific search issues, including unindexed UUID equality scans causing broad timeouts and complete system stalls during add_episode execution at scale (GitHub Issues #1272, #1592, #1819).  

  4. MCP Server Token Inflation: Teams wiring Graphiti's Model Context Protocol (MCP) server into workflows report that the server routinely returns raw fact_embedding arrays directly to the model, artificially inflating token consumption by up to 50 times (GitHub Issue #610).  

For the BACKEND-3 architecture, where exact source identity, precise reconstructible citations, and specific correction tracking are required—and where "clinical findings" extraction is rejected in favor of a user-defined vocabulary—the autonomous, probabilistic extraction of Graphiti introduces unacceptable entropy.

Alternatives: Mem0, Letta, and Microsoft GraphRAG

It is necessary to contrast Graphiti with alternative semantic memory layers.

  • Mem0 utilizes a two-phase pipeline (extract and reconcile) with a focus on token efficiency. It extracts candidate facts from each message pair and reconciles them against existing memory (arXiv:2504.19413, published April 2025). However, it updates memories by replacing them or appending them semantically, lacking a strict mathematical bi-temporal structure.  

  • Letta provides a tiered operating-system-like memory (Core, Recall, Archival) managed entirely by the agent through tool calls. The agent explicitly writes to memory blocks.  

  • Microsoft GraphRAG (arXiv:2404.16130) focuses on document corpus ingestion and hierarchical community summarization for global sensemaking, rather than incremental, transaction-time agent memory. In temporal reasoning benchmarks (arXiv:2607.05577), standard GraphRAG achieved only 18.8% accuracy compared to Graphiti's 57.4%.  

While Mem0 and Letta excel in standard conversational agent contexts, neither provides the rigorous chronological guarantees required to ensure that prayer text corrections do not advance listing timestamps, or that exact source revisions can be targeted for late repairs via a synchronization cursor.

Relational Bitemporal Schema: PostgreSQL & SQL:2011

To satisfy the stringent requirements for temporal knowledge, source provenance, and exact correction tracking, the architecture must abandon probabilistic LLM graph management in favor of a highly deterministic bitemporal relational schema, natively supported by PostgreSQL.

System Time versus Business Time

The SQL:2011 standard formalized the concept of bi-temporal tables, establishing two distinct axes of time:  

  • Business Time (Valid Time / Event Time): The period during which a fact is true in the real world (e.g., the exact duration of a calendar event, or the time a prayer was spoken).

  • System Time (Transaction Time / Observation Time): The exact database timestamp when the system recorded, updated, or deleted the fact.

In the BACKEND-3 ecosystem, the supplied contracts demand that corrections to prayer text may not advance the listing timestamps. This requires strict separation of these temporal axes. When a user edits a transcript from a week ago, the Business Time remains anchored in the past, but the System Time advances to the current transaction instant (now()). Consumer clients querying the UI sort by Business Time, ensuring the listing order does not change. Conversely, consumer clients syncing local states query by System Time to pull the delta.  

Schema Implementation via PostgreSQL Range Types

PostgreSQL achieves rigorous SQL:2011 bitemporal compliance using timestamp range types (specifically tstzrange) and GiST (Generalized Search Tree) exclusion constraints.  

A generic schema for context source tables (capturing prayer transcripts, teaching texts, and metadata) is defined to prevent overlapping valid timelines for a single entity, employing the WITHOUT OVERLAPS constraint paradigm:

SQL
-- Enable GiST indexing for exclusion constraints
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE context_sources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_type TEXT NOT NULL,           -- e.g., 'prayer', 'sermon', 'scripture'
    digest TEXT NOT NULL,                -- Cryptographic hash for consumer comparison
    content TEXT NOT NULL,
    metadata JSONB,
    valid_range TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),
    sys_period TSTZRANGE NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),

    -- Ensure no overlapping valid_range for the same ID
    EXCLUDE USING GIST (
        id WITH =,
        valid_range WITH &&
    )
);

The GiST exclusion constraint (valid_range WITH &&) mathematically guarantees that no two records for the same id can have overlapping valid_range windows.  

If a transcript or contextual record is corrected, the database executes a temporal split:

  1. The old record's sys_period is closed (the upper bound is set to the transaction time, now()).

  2. A new record is inserted with the corrected content, generating a new digest. Its valid_range exactly matches the original event time, but its sys_period starts at now().  

This architecture satisfies the requirement that design updates, removals, and superseded claims are entirely reconstructible. It maintains absolute fidelity to the exact source history without relying on an LLM to probabilistically manage edge invalidation, eliminating the risk of collateral invalidation entirely.

Source Provenance, Ontology, and Correction Flow

The BACKEND-3 domain projection relies heavily on independent source pipelines. Source classes include prayer transcripts, teaching text, Scripture, calendar data, and other personal-context records. There is no selected consolidated knowledge backend; instead, the bitemporal Postgres store acts as the immutable ledger from which downstream projects project their specific domains.

The Theographic Ontology Example

Scripture references and personal context must retain source/edition locators and digest-qualified locators. The target schema candidate, Theographic (an open-source CC BY-SA 4.0 metadata dataset), provides an exact structural model for biblical data.  

The Theographic dataset normalizes biblical metadata into distinct entity classes:

  • People: Biblical figures with aliases.

  • Places: Geographic points.

  • Events: Temporal occurrences (e.g., "The Exodus").

  • Passages: Digest-qualified locators (e.g., Genesis 1:1, BSB translation).  

When the OpenAI Realtime agent processes a conversational workflow—such as a user discussing a sermon regarding King David—the backend does not indiscriminately dump semantic text into a vector database. Instead, an explicit tool call is executed to extract entities based on the user-defined vocabulary, mapping them directly to the Theographic schema.  

The resulting relational link is stored bitemporally:

INSERT INTO contextual_links (source_id, entity_type, entity_id, valid_range)

Reconstructible Citations and Digest Comparison

The user contract mandates that consumers compare text digests and membership. Because the bitemporal table stores a cryptographic hash (digest) of the content, downstream consumers (like an iPad app, a separate website renderer, or a creative workflow storyboarder) can synchronize their local state highly efficiently.

If a source text is updated, the digest inherently changes. The consumer application checks its local digest against the server's digest for a given id. If they differ, the consumer fetches the updated payload. Scripture text citations retain their source edition by storing the specific translation metadata (e.g., "BSB", "WEB") directly in the JSONB metadata column, rendering the citation immune to unprompted LLM summarization or degradation over time.  

Change Cursor Semantics and Test Matrix

A defining feature of this architecture is the necessity to support "late repairs" across decentralized consumer endpoints without breaking chronological flow or UI sorting logic.

Adapter and Cursor Semantics

A simple sequence ID or a traditional updated_at column fails catastrophically for temporal data. An updated_at mutation violates the principle of immutability, and a sequential ID does not cleanly map to point-in-time historical reconstruction.

The change cursor must iterate strictly over the Transaction Time (sys_period), not the Event Time (valid_range).

When a downstream consumer requests a delta sync for late repairs or updates:

  1. Request: The client issues GET /sync?cursor=2026-10-10T12:00:00Z.

  2. Query: The adapter translates this to SELECT * FROM context_sources WHERE lower(sys_period) >= '2026-10-10T12:00:00Z'.

  3. Response: The server returns all records (insertions, supersessions, and deletions) that the database observed since the cursor timestamp.  

Because a deletion or an update in a bitemporal system is merely the insertion of a new row with a closed valid_range or sys_period upper bound, the consumer naturally receives the "tombstone" or the updated state, advancing its local cursor to the maximum lower(sys_period) received in the batch.
