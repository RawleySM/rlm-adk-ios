Continuous Device Recording and Explicit Quiet Decoupling

A core product requirement is the implementation of continuous device recording combined with the concept of "explicit quiet." Quiet suppresses all speech until an explicit wake command is detected, and calendar timers must not override it. Furthermore, prayer capture tolerates long silences, ending only by explicit manual control, after which the system saves the capture and waits.

Because the OpenAI API charges for all processed tokens—including silence, which still bills as active audio input if transmitted over a WebSocket—streaming hours of explicit quiet or prayer capture directly to the Realtime API would accrue massive, unnecessary costs. Therefore, recording, transcription, and conversational voice sessions must be treated as mechanically independent pipelines.  

The iOS client must implement local Voice Activity Detection (VAD) and semantic gating. During explicit quiet periods, the physical microphone hardware remains active locally on the iPhone, but the WebSocket transmission to the OpenAI endpoint must be completely suppressed. A localized, on-device machine learning model (such as an embedded CoreML wake-word detector or a highly quantized audio classifier) must monitor the local buffer. Until this local model detects the specific wake phrase or manual user interruption, no audio leaves the device.

Prayer capture introduces a different paradigm. Because it tolerates long silences and relies on explicit termination, this audio should be streamed directly to local non-volatile storage as a standard M4A or WAV file, bypassing the generative Realtime API completely. Upon explicit termination of the prayer session, the native iOS client closes the file handle. The saved file can then be uploaded to the asynchronous gpt-transcribe batch endpoint at the heavily discounted $0.0045 per minute rate, converting the prayer into a text transcript suitable for the user's personal-context sources. This architecture completely avoids the generative audio token costs associated with live duplex models during silent contemplation.  

Outside of quiet or prayer modes, the system enters its proactive state. The initial proactive speech covering calendar preparation, departure logistics, and project phases needing input requires the iOS client to open the Realtime API WebSocket, pass the static system prompt and the dynamic daily context, and prompt the model to speak first. Because background work continues independently of the voice session, a paid voice session need not remain open merely because local recording continues. The native app can close the expensive WebRTC/WebSocket connection when a conversation naturally concludes, falling back to local VAD monitoring to trigger the next session.

Native iOS Background Audio Constraints (RawleySM/rlm-adk-ios)

The execution of continuous background recording and selective wake capabilities relies heavily on the underlying iOS operating system's handling of the AVAudioSession. The native workspace within RawleySM/rlm-adk-ios must navigate strict constraints imposed by Apple's sandboxing and aggressive power-management heuristics. Paid membership in the Apple Developer Program allows for deployment and provisioning, but it offers zero exemptions from OS-level audio constraints.

The AVAudioSessionCategoryPlayAndRecord Imperative

To enable simultaneous playback of scriptural devotionals and the uninterrupted recording of the user's voice for interruption and correction, the application must configure the shared audio instance with AVAudioSessionCategoryPlayAndRecord. However, simply declaring this category is insufficient for background longevity. The application must possess the necessary capabilities within the UIBackgroundModes array of its Info.plist file, specifically the "Audio, AirPlay, and Picture in Picture" flag.  

Furthermore, the OS imposes strict rules regarding audio routing and interruption. Because the user is highly likely to utilize Bluetooth peripherals (e.g., AirPods, car audio systems), the audio session must be explicitly configured with appropriate option flags. If the developer utilizes AVAudioSessionCategoryOptionAllowBluetooth, iOS defaults to the Hands-Free Profile (HFP), which heavily degrades audio quality to an 8,000 Hz sample rate. To maintain high-fidelity audio playback for devotions while retaining microphone access, the session must request AVAudioSessionCategoryOptionAllowBluetoothA2DP for advanced distribution profiling.  

The Background Suspension Challenge

The decoupling of explicit quiet from active transmission introduces a severe engineering challenge. The device must maintain an active, hot audio session to capture the eventual wake command or the termination of a prayer session. Apple's documentation and developer consensus indicate that iOS aggressively monitors background audio applications. If an app declares AVAudioSessionCategoryPlayAndRecord but fails to actively process audio buffers, or attempts to activate the session while completely in the background without prior foreground authorization, the OS will block the activation or terminate the process.  

Developers have documented behaviors where iOS terminates processes with a SIGKILL signal at approximately 50 seconds of continuous background time if the application is not actively utilizing the audio hardware in a manner recognized by the system. If the application merely suspends its audio engine during quiet periods to save battery, iOS will classify the application as idle and terminate the background process entirely, completely defeating the continuous recording requirement.  

Therefore, the native Swift client must continuously write silent or ambient audio buffers to a local null sink or a temporary ring buffer to maintain the active AVAudioSession lease. The AVAudioEngine must remain running. By keeping the hardware engaged in a continuous loop, the application satisfies the operating system's requirement for active background processing, thereby holding the process awake to monitor for wake words without necessitating continuous network transmission.

Network Permissions and Routing Irregularities

Modern iOS versions also enforce strict local network permissions. Applications integrating complex audio bridging or inter-app audio must include NSLocalNetworkUsageDescription and NSBonjourServices entries to prevent the OS from blocking localized audio routing protocols. Additionally, hardware routing events can trigger unexpected session behaviors. For example, connecting to certain automotive systems via Bluetooth can cause the vehicle to interpret the active PlayAndRecord session as a phone call, muting native Digital Audio Broadcasting (DAB) radio and altering volume controls. The iOS developer must implement robust AVAudioSession.routeChangeNotification observers to gracefully handle these peripheral transitions without dropping the ongoing prayer capture or active voice session.

Repository Structure and Documentation

The repository is hosted on GitHub and partitioned into distinct schema formats. The publisher explicitly notes that while flat CSV files are provided for legacy SQL imports, the nested JSON objects within the json directory represent the preferred, authoritative source for databases capable of handling complex document schemas. The core schema revolves around discrete JSON files: people.json, places.json, events.json, and periods.json.  

The total coverage spans approximately 3,067 distinct people and 450 major events, cross-referenced against nearly 53,000 verse links. The geographic dimension of Theographic, specifically within places.json, embeds standard decimal latitude and longitude coordinates directly into the entity records (e.g., "latitude": 33.511612, "longitude": 36.309102).  

Native IDs and Schema Irregularities

A defining characteristic of the Theographic schema is its reliance on proprietary native string identifiers. Rather than utilizing standard UUIDs (Universally Unique Identifiers) or purely semantic English labels, entities carry a primary lowercase string designation appended with an underscore and a unique numeric identifier. Examples extracted from the dataset include hadad-rimmon_501, gederothaim_454, and jether_654.  

This systematic suffixing is a deliberate design choice to mitigate the rampant name collisions inherent in ancient texts, where multiple distinct individuals or regional towns share a single moniker. By enforcing this native ID structure, Theographic prevents graph edges from unintentionally collapsing distinct personas into a single node.

However, the schema exhibits several irregularities and limitations. First, it relies entirely on OSIS (Open Scripture Information Standard) versification for its passage linkages. The schema defines OsisRef arrays formatted as Book.Chapter.Verse to anchor entities to the text. This introduces a significant limitation regarding historical assertions and historic certainty. An edge connecting a person to an OSIS reference in Theographic signifies mere presence or participation in the text; it does not infer historical certainty, the precise nature of the interaction, or the theological weight of the passage. The OSIS string alone does not guarantee uniform semantic alignment across different translations, as chapter and verse divisions fluctuate heavily between the Masoretic Text, the Septuagint, and modern English vernaculars. The geographic points are also highly simplified; embedding a single coordinate pair fails to account for the physical expansion of cities over centuries or the ambiguous nature of certain historical ruins.

Because this iOS application is designed as a private, single-user portal, the immediate legal risk of forced distribution is negated—ShareAlike clauses trigger upon public distribution, not private internal use. To rectify Theographic's simplistic single-coordinate approach to geography, the backend should query the OpenBible.info Bible Geocoding Data, curated by Stephen Smith. Also licensed under CC BY 4.0, this repository defines precise geometries using the GeoJSON format.

Source-Qualified Entity Design and Domain Projections

The native workspace requires an architecture that treats source pipelines as strictly independent of execution. Because domain projections belong entirely to the consuming projects, there is no single monolithic database asserting universal scriptural truth. The backend must implement a source-qualified entity schema to manage updates, version semantics, and data provenance.

Preventing Name-Only Merges

A primary risk in metadata ingestion, particularly when utilizing a powerful LLM to synthesize data, is the conflation of identities based on shared string values. If the user possesses a personal calendar contact named "David," the backend must never automatically link modern calendar events involving this contact to the scriptural King David.

To enforce this isolation, every entity within the execution backend must be wrapped in a source-qualification envelope. An entity object must possess a strictly typed provenance field indicating its absolute origin (e.g., source: theographic, source: stepbible, source: personal_calendar). Internal system identifiers must be generated via composite keys linking the origin source and the source's native ID. For example, Theographic's hadad-rimmon_501 is projected into the backend as urn:rlm:theographic:hadad-rimmon_501, ensuring absolute cryptographic and semantic distance from personal data.

When designing passage mappings and aliases, evidence spans—the specific OSIS passage references justifying a relationship edge—must be retained immutably alongside the edge definition. If an upstream repository issues a correction, the update semantic dictates that the backend does not overwrite the existing node in a destructive manner. Instead, it increments a source-version tag on the entity envelope. When the user initiates a voice session requesting a summary, the LLM is provided with these fully namespaced contexts. By supplying the model with urn:rlm:theographic:david_123 instead of the bare string "David", the system prevents hallucinatory cross-contamination between modern daily planning and ancient biblical history.

Projection Alternatives: SQL vs. Neo4j

Theographic's publisher explicitly provides Python import scripts designed for Neo4j, a native graph database utilizing the Cypher query language. Deploying a Neo4j projection is optimal for topological analysis. When a creative workflow requires finding the shortest relational path between two biblical figures, or extracting a visual tree of descendants, Neo4j calculates these traversals with high efficiency by walking the pre-established edge pointers without complex recursive joins.  

However, the user's primary execution backend (RLM-ADK) relies heavily on durable action items, chronological personal schedules, and rigid workflow state machines. For these operational components, traditional relational SQL projections remain vastly superior. Importing Theographic's array-based JSON fields directly into a flat SQL table violates first normal form and creates inefficient querying scenarios. Therefore, an SQL projection necessitates normalizing the nested arrays into dedicated relational lookup tables.  

A dual-projection strategy is the recommended architecture. The core execution state, personal calendar data, prayer transcripts, and durable action items reside securely in encrypted relational SQL tables. When a research request is initiated via voice, the execution backend asynchronously queries the isolated, read-only Neo4j container to retrieve the scriptural graph paths. The resulting graph traversal is serialized into standard JSON and appended to the prompt context passed to the OpenAI API. This dual-model approach satisfies the requirement that domain projections remain separated while allowing the consuming project to leverage the strengths of both storage paradigms.
