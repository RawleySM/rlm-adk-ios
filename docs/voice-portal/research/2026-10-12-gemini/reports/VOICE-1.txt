Architectural Taxonomy of Full-Duplex Spoken Dialogue Systems

To rigorously evaluate the wave of open-weight models released within the last 180 days, it is necessary to apply a structured architectural taxonomy. The academic literature from 2026, specifically the Speaking While Listening survey (EMNLP 2026), provides a standard ontology for classifying full-duplex systems across four architectural layers (L0 to L3) and a continuous state machine.

The L0 layer defines the traditional cascaded pipeline. In an L0 system, an external Voice Activity Detection (VAD) module acts as a rigid scheduler, sequentially passing audio to an Automatic Speech Recognition (ASR) model, text to a Large Language Model (LLM), and text back to a Text-to-Speech (TTS) synthesizer. This architecture is essentially half-duplex, resulting in robotic conversational rhythms and a complete inability to process interruptions gracefully.

The L1 layer introduces a sidecar predictor. In this architecture, a secondary, lightweight neural network reads the hidden states of the primary LLM to predict when the user is pausing, allowing for faster, predictive turn-taking without relying on rigid silence thresholds.

The L2 layer integrates the full-duplex decision matrix natively into the token stream. The model continuously ingests audio tokens and predictively outputs either semantic text/audio tokens or silence tokens, allowing for dynamic yielding of the conversational floor.

The L3 layer represents the pinnacle of current speech-to-speech research. In an L3 system, the acoustic and semantic spaces are fully unified into a shared latent representation. Listening and speaking occur concurrently at the deepest neural level, enabling immediate, sub-second micro-adjustments in prosody based on the user's ongoing speech. Furthermore, true full-duplex capabilities are judged on a Time, Interruption, and Role (T x I x R) ontology, requiring the system to handle six canonical interaction scenarios, including overlapping speech, affirmative backchanneling, and sudden semantic redirection.

Mimi: Developed by Kyutai and utilized by Moshi and PersonaPlex, Mimi processes audio into a 12.5 Hz representation at an exceptionally low 1.1 kbps bandwidth, maintaining a fully causal streaming latency of just 80ms.

CosyVoice 2: For workflows that output text and require a cascaded streaming TTS engine, CosyVoice 2 (0.5B parameters) offers human-parity zero-shot voice cloning. It eliminates traditional grapheme-to-phoneme frontends by processing raw text directly via BPE tokenization, masking out one-to-many tokens to prevent pronunciation errors caused by data sparsity.

Concrete Design Implications for the iOS SwiftUI Application

The deployment target is a private, single-user native SwiftUI iPhone portal. This environment imposes strict constraints on memory, background execution, and audio session management. The product requirements demand continuous device recording, silence-tolerant prayer capture, proactive speech, and deep integration with Theographic data and durable action items.

1. Resolving the OS Audio Constraint and "Quiet" Mode

The user desires continuous device recording, including an explicit "quiet" state that suppresses all speech until an explicit wake, un-overridden by calendar timers.

The iOS Constraint: Apple's iOS strictly manages background microphone usage. An application cannot record ambiently in the background without maintaining an active AVAudioSession, which triggers a persistent orange microphone indicator in the status bar. Paid Apple Developer Program membership does not bypass these kernel-level privacy safeguards and memory limits. If the application consumes too much memory while backgrounded, the OS watchdog will terminate it.

Architectural Design: Sending continuous audio to the OpenAI gpt-live-1 API at $0.05 per minute during hours of silence is financially untenable. The SwiftUI app must implement a local, highly quantized Voice Activity Detection (VAD) model or a local MLX port of the Mimi encoder.

During "quiet" mode, the iPhone buffers audio locally. The network connection to the voice generation API remains closed. Only when the local model detects the explicit wake phrase does the app initiate the WebRTC connection to either OpenAI or the self-hosted PersonaPlex instance.

2. Engineering the "Prayer Capture" Workflow

Prayer capture tolerates long silences, ends only by explicit control, and then saves the transcript.

Architectural Design: This workflow must be completely decoupled from the conversational voice session. An active full-duplex session (whether OpenAI or PersonaPlex) expects a conversational cadence and will attempt to fill long silences or close the connection to save resources.

When the user initiates "Prayer Capture," the app should disable the full-duplex routing. Instead, it should utilize a local streaming transcription model (like a heavily quantized Whisper running via CoreML) or stream the audio to a low-cost batch-processing endpoint. The audio buffer is kept open indefinitely until the user explicitly stops it, at which point the final text transcript is bundled and saved as a source product.

3. Proactive Speech and Calendar Transitions

Outside of quiet/prayer states, the system must proactively speak to cover calendar preparation, departure, and project phases needing input.

Architectural Design: Because a paid voice session does not remain open continuously, the RLM-ADK backend must possess a signaling mechanism to wake the iOS application.

When the RLM-ADK server determines that a calendar event requires proactive preparation, it sends a silent push notification to the iOS device. The SwiftUI app receives the notification in the background, activates the AVAudioSession, establishes the WebRTC connection to gpt-live-1 or PersonaPlex, and initiates the conversation by passing a specific text prompt to the model (e.g., "Inform the user they need to leave for their meeting in 10 minutes and ask if they need context on the project phase.").

4. Durable Action Items and Theographic Context

Long research and creative requests become durable action items producing actual reviewable outputs (websites, books, reports) after voice sessions end. Source pipelines are independent of execution, and there is no consolidated knowledge backend—meaning Theographic data, Neo4j graphs, and temporal frameworks must be queried individually.

Architectural Design: Full-duplex voice models (like gpt-live-1's frontend or PersonaPlex's Helium backbone) are optimized for acoustic naturalness and low latency, not deep multi-stage database querying.

The system must utilize rigorous Tool Calling / Function Calling. When the user asks a complex theological question during a voice session, the voice model must emit a JSON tool call (e.g., query_theographic_schema(parameters)).

Using OpenAI's Realtime API, this is natively supported via the Remote Model Context Protocol (MCP) server integration. The API handles the tool call asynchronously, passing it to the RLM-ADK backend. The voice session keeps the conversation fluid ("Let me look that up...") while the RLM-ADK backend runs the complex Neo4j or Theographic query using a dedicated, high-reasoning text model (like gpt-5.6-sol). Once the backend completes the task, it injects the resulting context back into the ongoing voice session.

For durable action items, the tool call simply acts as a webhook, transferring the task parameters to the RLM-ADK queue for asynchronous processing long after the voice session has terminated.

Important Unresolved Facts and Evidence Gaps

While the strategic path is clear, several technical unknowns require bounded investigation:

On-Device L3 Memory Constraints: The official Kyutai Moshi repository contains a moshi_mlx/ directory explicitly for iPhone and Mac on-device inference. However, the exact memory footprint of running a 7B-parameter L3 model concurrently with iOS background audio processing is undocumented in the literature. If the application exceeds the ~2-3GB active memory limit enforced by the iOS watchdog, it will crash.

PersonaPlex Structured Output Fidelity: PersonaPlex achieves excellent naturalness using its 7B Helium backbone. However, its reliability in consistently generating strictly formatted JSON tool calls for the RLM-ADK backend during a rapid, overlapping conversation has not been benchmarked against OpenAI's proprietary tool-calling success rates.

SwiftUI Background WebRTC Stability: Maintaining a persistent WebRTC connection for the gpt-live-1 API while the iPhone screen is locked and transitioning between cellular and Wi-Fi networks poses significant stability challenges. The ephemeral client keys expire every 60 seconds, requiring robust reconnection logic.

Bounded Comparison Plan

To definitively choose between the OpenAI gpt-live-1 API and a self-hosted PersonaPlex implementation, the following non-destructive proof-of-concept plan should be executed without deploying production software or purchasing excessive credits:

Phase 1: API Cost and Logic Validation (OpenAI)

Write a minimal Python script to open a WebSocket connection to the gpt-live-1 endpoint.

Simulate a 10-minute conversational session, injecting a mock Remote MCP tool call representing a Theographic database query.

Measurement: Verify the exact billing deduction on the OpenAI dashboard to confirm the $0.05/minute voice layer cost isolates effectively from the backend token costs, and confirm that asynchronous tool calls do not freeze the audio playback.

Phase 2: Local Hardware Viability Assessment (PersonaPlex)

Clone the kyutai-labs/moshi repository onto a local Apple Silicon Mac.

Utilize the moshi_mlx directory to load the CC-BY-4.0 PersonaPlex weights.

Measurement: Run the model locally and monitor the Mac's Activity Monitor for Unified Memory consumption and CPU/GPU load. If the memory footprint exceeds the RAM capacity of the target iPhone, local device execution must be abandoned in favor of hosting the model on the Mac and operating the iPhone as a remote client over the local network.

Phase 3: Hybrid Prompting and Persona Transition Testing

Inject varying text prompts into the PersonaPlex pipeline ("You are a solemn devotional reader" vs. "You are an aggressive project manager") alongside the same voice prompt.

Measurement: Assess the time taken for the model to successfully switch contexts without requiring a full model reload, verifying its suitability for transitioning between the app's disparate workflows.
